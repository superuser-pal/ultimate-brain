## 1. Repository Overview

A cross-platform desktop app (Tauri v2: Rust backend + React/TypeScript frontend, ~137k lines) implementing Karpathy's LLM Wiki pattern for non-technical users. You drop documents into `raw/sources/`; an ingest queue runs a **two-step LLM pipeline** (analysis → generation) that writes source summaries, entity and concept pages, and review items into `wiki/`. It adds an LLM page merger with safety checks, an asynchronous review queue, LLM duplicate detection and merge, structural and LLM "semantic" lint (contradictions, stale claims), graph relevance and community detection, optional vector search (LanceDB), deep web research, a web clipper, and a local HTTP API + MCP server. It is a self-contained product with its own LLM client, not an agent skill set. It is relevant mainly for its **generation prompts and merge mechanics**, and as the best example of a working review queue. It does not use Claude Code or Codex as the intelligence layer (it can use their CLIs as LLM transports: `claude-cli-transport.ts`, `codex-cli-transport.ts`).

### Answers to the brief's questions

1. **How are new wiki pages generated?** Two LLM calls per source: structured analysis (aware of purpose, schema and the index), then generation of complete page files plus review items, parsed from a strict block format. Long sources go through chunk digests first.
2. **How is existing content incorporated?** At analysis time only through `index.md` (titles and one-liners), so the model judges overlap and contradictions from the index, not page bodies. At write time, an existing page is merged with the new one by a separate LLM call (`page-merge.ts`).
3. **Incremental or full rewrites?** Incremental at the file level (only pages touched by this source), but each touched page body is **regenerated by an LLM merge** of old + new, guarded by length/structure checks and a backup. Single-source pages are replaced outright on re-ingest. Index and overview are rebuilt deterministically by the app.
4. **How are relationships maintained?** `sources:` and `related:` frontmatter arrays (union-merged), body `[[wikilinks]]`, LLM link enrichment, dedup link rewriting, cascade cleanup on delete, graph relevance computed on the fly.
5. **Is contradiction handling actually implemented?** **Detection: yes** (ingest analysis → `contradiction` review items; semantic lint over page previews). **Resolution: no automated resolution**; the template rule routes it to open-question and synthesis pages, and review options are only "Create Page / Skip". Semantic lint sees only the first 500 characters of each page, so contradictions deeper in a page are missed.
6. **Can outputs support selective Notion publication?** Partially (Inferred): typed pages with `type`, `sources`, `related` and schema folders map to Notion databases; review items map directly to review-queue rows. No publish flags, no stable IDs, no Notion integration.

## 4. Architecture Integration

- **Ingestion (main contribution):** two-step structure for the meeting ingest; analysis outputs map to our extraction list (summary, decisions, facts, open questions, contradictions, action items); generation outputs become new notes (applied directly) + proposals (review queue).
- **Agent instructions:** subject-boundary and verbatim-data rules; "model never writes aggregates".
- **Markdown schema:** meeting / decision / project / stakeholder types from the Business template, reconciled with our IDs (0001), lifecycle/assessment (0005), timelines (0010).
- **Notion bridge:** review item shape + sweep as the model for the Notion Review database; Notion meeting notes as single-source pages that can be regenerated on re-ingest.
- **Maintenance (v2):** semantic contradiction/stale lint, dedup proposals.

## 5. Dependencies and Risks

- **GPL-3.0:** do not copy code or prompts verbatim into the product; reimplement from the design.
- **Existing content is only seen via the index** during analysis, so contradiction detection is limited to what titles and one-liners reveal.
- **LLM rewrites page bodies on every touch** (merge), which can drift or drop nuance; mitigated only by a length heuristic and backups. Writes are direct; review covers only flagged items.
- **Answers saved and auto-ingested** create a feedback loop of AI content treated as sources.
- **No stable IDs** (slug/path identity), wikilinks by default, app-managed history instead of Git.
- **Heavy stack:** Rust, Node, protoc, LanceDB, optional MinerU; not reusable as components.
- **Not run:** large test suite including real-LLM tests not executed.

## 6. Open Decisions

1. **What the analysis step sees:** for meeting ingest, should step 1 read only the brain's index (cheap, like llm_wiki) or also the bodies of the most relevant notes (people, project, recent decisions) found via retrieval? (Recommended: index + bodies of the notes for attendees and the matched project, capped by a budget; this is what makes contradiction detection real.)
2. **Purpose file:** add a short "what matters to me" purpose section (goals, key questions per area) that steers extraction, or rely on the PARA structure alone?
3. **Regenerating meeting summaries:** when a Notion meeting note is edited after ingest, regenerate its meeting summary directly (single-source page) and route only changes to shared notes as proposals? (Recommended: yes.)

## 7. Recommended Next Step

Use llm_wiki as a design reference for the meeting-ingest skill: two-step analyse/generate, strict output blocks for new notes vs review items, subject-boundary and verbatim rules, deterministic aggregates, review sweep, and the Business template's meeting/decision/project/stakeholder types. Reject its auto-ingest of answers and direct LLM body merges. No code reuse (GPL-3.0).
