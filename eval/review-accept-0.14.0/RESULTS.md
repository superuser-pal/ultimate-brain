# A submitted Review acceptance applies without a second yes: blind run results

CC-215 acceptance (decision 0055: no second approval of the user's own wording; spec/capture-and-review.md §7.3). Fresh `claude -p` sessions on 2026-11-11, each in its own brain built from the synthetic `brain-acme` fixture by [setup.py](setup.py). The CLI is this branch's, run through a `brain` shim. The skills are the fork PR's `brain/` (passed as `UB_SKILLS_SRC`), not the vendored 1.6.0 snapshot. No MCP servers, no git remote, and `gh` is a stub that always fails. Notion is simulated: the Review database's rows and each Review page (properties and body as Markdown) are files the agent reads, and its Notion writes are lines in `writes.md`. The CLI rendered each page and recorded it as published, then the setup typed the decisions into it, as the user would.

**To reproduce:** `npm run build`, then `UB_SKILLS_SRC=<the fork's brain/ folder> eval/review-accept-0.14.0/run.sh` (or `run.sh exact held` for some). Without `UB_SKILLS_SRC` the brains get the vendored snapshot.

**Not a review, and simulated.** These runs test the skill text against a Notion made of static files. The model that ran them is the model that wrote the skill change. What they cannot show: real MCP calls and their timing (the re-read is a file the harness swaps in), the live Submit buttons, and actual publishing (writes are lines in `writes.md`, and new page ids are made up). What they do show: the skill text, followed by a model, reaches the stated outcome in each setup, including the cases that must not apply.

Every prompt but the first word is the same: the simulated-Notion instructions and "The user is here. If you need to ask them anything, ask it and end your reply: they will answer in their next message." So a run that asks for a second yes stops there and applies nothing.

**Before the change (`runs-before/exact`).** The same `exact` setup with the vendored skills (1.6.0, which say "apply after a yes"): the run showed the same table of decisions and ended with "Shall I apply a, b and c as shown?", applying nothing. This is the second yes the change removes.

**What the runs found outside this task** (not fixed here; reported to the coordinator):
- **A rejected draft decision is listed under Current in the project's decision log** (`runs/exact/note-diff.txt`, `projects/acme-website/decision-log.md`): after c's Reject archived the draft "Launch in March", `brain views` added it to the log as `accepted`, and the publish sent that section.
- **brain-apply names no private working folder.** In the first round the five runs went in parallel, and the `revision` run read another session's render output from a fixed temporary path (it said so, and wrote a correction). brain-catch-up says `mktemp -d`; brain-apply doesn't. The `revision` trace here is a second, sequential run.
- From the CLI test written for this task: applying an old plan a second time, after the revision it asked for was drafted, records the request again and sets the drafted revision back to `requested`. The skills forbid applying a plan twice, so a session following them does not reach it.

**Notes.** The push failed in every run (no remote). The fixture's notes are dated December 2026 and the runs' clock is not, so some dates read out of order. Lint's errors about the installed skills differing from the released snapshot are expected: the brains carry the fork PR's unreleased skills.
