# A submitted Review acceptance applies without a second yes: blind run results

CC-215 acceptance (decision 0055: no second approval of the user's own wording; spec/capture-and-review.md §7.3). Five fresh `claude -p` sessions run in parallel on 2026-11-11, each in its own brain built from the synthetic `brain-acme` fixture by [setup.py](setup.py). The CLI is this branch's, run through a `brain` shim. The skills are the fork PR's `brain/` at 8f1bd44 (passed as `UB_SKILLS_SRC`), not the vendored 1.6.0 snapshot. No MCP servers, no git remote, and `gh` is a stub that always fails. Notion is simulated: the Review database's rows and each Review page (properties and body as Markdown) are files the agent reads, and its Notion writes are lines in `writes.md`. The CLI rendered each page and recorded it as published, then the setup typed the decisions into it, as the user would.

**To reproduce:** `npm run build`, then `UB_SKILLS_SRC=<the fork's brain/ folder> eval/review-accept-0.14.0/run.sh` (or `run.sh exact held` for some). Without `UB_SKILLS_SRC` the brains get the vendored snapshot.

**Not a review, and simulated.** These runs test the skill text against a Notion made of static files. The model that ran them is the model that wrote the skill change. What they cannot show: real MCP calls and their timing (the re-read is a file the harness swaps in), the live Submit buttons, and actual publishing (writes are lines in `writes.md`, and new page ids are made up). What they do show: the skill text, followed by a model, reaches the stated outcome in each setup, including the cases that must not apply.

Every prompt but the first word is the same: the simulated-Notion instructions and "The user is here. If you need to ask them anything, ask it and end your reply: they will answer in their next message." So a run that asks for a second yes stops there and applies nothing.

**Before the change (`runs-before/exact`).** The same `exact` setup with the vendored skills (1.6.0, which say "apply after a yes"): the run showed the same table of decisions and ended with "Shall I apply a, b and c as shown?", applying nothing. This is the second yes the change removes.

**Fixed here: brain-apply's working folder.** In the first round, on the fork's first head, the five runs went in parallel and the `revision` run read another session's render output from a fixed temporary path (it said so, and wrote a correction). brain-catch-up said `mktemp -d`; brain-apply didn't. At the coordinator's request the fork PR now gives brain-apply the same rule (8f1bd44), and in this round, five sessions in parallel, no run read another's plan or render, and no reply or `writes.md` mentions another brain.

**Found outside this task** (not fixed here; CC-218's):
