# Run on a schedule

When the user says "review my week every Monday", "run the weekly review on a schedule" or "turn on the weekly review". What a scheduled run does is SKILL.md's "Unattended". Start with `brain status` (step 1 of the run: the working branch) and note `modules.reports`, `settings.publish`, `settings.weekly` and `product.path`.

1. **Ask what is missing, once,** in one message:
   - the time, when not Monday at 08:00 (`--at` and `--days`, local time);
   - the Claude model to pin, offering **Sonnet by default** as a full id (the current one, such as `claude-sonnet-5-5`). The user may pick another, such as Opus (`claude-opus-5-5`). An alias such as `sonnet` is refused, because it moves under the schedule.

   Say what a run does: every Monday it writes one short review in the brain (what changed, your tasks, at most five decisions), writes the Review rows those decisions need, applies nothing, and writes nothing in a quiet week. Each run stops at a cost ceiling: 3 USD on Sonnet, 8 on Opus.
2. **Offer once each,** in the same message, what makes a run useful, and change each only after its yes:
   - **Reports,** when `modules.reports` is false: `Turn on Reports so each week's review appears in Notion?` A yes turns it on as brain-connect-notion turns on a module ("turn on reports": `brain modules on reports`, then its Notion check with `<product.path>/notion/modules/reports.md`). A no: say `The review stays a file in your brain (reports/), and your next session tells you when one is ready.` and keep going.
   - **`settings.publish: auto`,** when it is `ask`: a scheduled run publishes nothing otherwise, so its Review rows and the report wait for your next session. `brain config set settings.publish '"auto"'`.
   - **The tools it may use.** A scheduled `claude -p` can't ask permission: it uses only what the brain's `.claude/settings.json` allows, and refuses the rest, which the run logs as a failure. Offer to add to `permissions.allow`: `Bash(brain:*)`, `Bash(git:*)`, `Bash(date:*)`, `Bash(jq:*)`, `Read`, `Edit`, `Write`, `Read(~/.ultimate-brain/weekly/**)`, `Edit(~/.ultimate-brain/weekly/**)` (its snapshot and working files), and the Notion server's tools (`mcp__<server>`, named as `claude mcp list` names it). Merge them into the file as it is, keeping every other key. The run writes in Notion only its publish: the Review rows and the report.
3. **Install it:** with Opus, first `brain config set settings.weekly.max_usd 8`. Then `brain schedule install weekly-review --at 08:00 --days mon --model <id> --max-budget-usd <settings.weekly.max_usd> --brain <brain> --json`, and `brain config set settings.weekly.schedule '"on"'`. Commit `brain.json` and `.claude/settings.json` when they changed (`weekly: schedule on`). On macOS `install` writes and loads a launchd agent; with `SCHEDULE_NOT_LOADED` in `warnings`, say it is written but not loaded, with launchctl's message. Elsewhere it returns cron lines: give them to the user to add with `crontab -e`. `CLAUDE_NOT_FOUND` means Claude Code isn't on `PATH`.

   **Trust the brain folder once.** `install` always warns `FOLDER_TRUST`: a scheduled `claude -p` ignores the brain's allow rules until Claude Code has been opened in the brain folder and its trust dialog accepted, and the CLI can't tell whether that happened. Pass it on in one line: `Before Monday's run, open Claude Code in <brain> once and accept the trust dialog, or the scheduled run can't use the tools you just allowed.`
4. **Say how to check and stop it:** `brain schedule list` shows it; your next session opens with `This week's review is ready: …` after a run; a run's output is in `~/Library/Logs/ultimate-brain/`. Asking again with another time replaces it. "Stop the weekly review": `brain schedule remove weekly-review`, then `brain config set settings.weekly.schedule '"off"'` and commit `brain.json` (`weekly: schedule off`).

**Other schedulers.** Any scheduler that runs `claude -p "weekly review unattended" --model <id> --max-budget-usd <n>` in the brain folder, signed in as the user and with their Notion connection, does the same job. It is a separate job from the scheduled catch-up: neither runs the other.
