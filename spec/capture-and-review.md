## 1. Domains

**1.1 Module.** `modules.domains`, **off by default** (schema §12, 0048's non-destructive switch rules), including when the `modules` block is absent (`modulesOf` special-cases it). Offered in onboarding's module checklist ("group your Areas by the work or life context they belong to"); turning it on asks nothing. Existing brains gain no required classification step. Off means: no Domain note is written or published; `area.domain` is ignored by `sync plan` (`ignored`, `MODULE_OFF`) and left out of `render`; queries do not group by Domain.

**1.2 Note type.** `domain` · prefix `dom-` · folder `domains/` · Notion: Domains. Fields in addition to schema §3: `org` (optional, one `org-` id), `notion_fields.archived` (bool) and, from 0.9.0, `notion_fields.type` (§1.4). Body: description. A Domain groups the user's work in a context; an **Org describes an organization and is not replaced**. `domain.org` and the Orgs "Domains" relation follow the Orgs module: with Orgs off both are left out like any module-off relation (0048).

**1.3 Area relation.** `area.domain`: optional, **at most one** `dom-` id (a scalar). Projects stay in Areas and have no `domain` field; Documents have none. **Domain grouping follows the Area**: a Project's or Document's Domain is derived through its `area`, so a second assignment cannot be written. When a Document's `area` and the Area of one of its `projects` sit in different Domains, lint reports the info `DOCUMENT_DOMAIN_MISMATCH` (the Document's own `area` decides). Two contexts' similarly named responsibilities are two Areas.

**1.4 Notion.** A "Domains" database (Name, Summary, Type, Org relation, Archived, Brain ID, Last Synced; no Lifecycle since 0.9.0, decision 0070). Type (select: Personal, Entrepreneurship, Professional) is yours, pulled into `notion_fields.type` and never pushed; it replaced Areas · Type in 0.9.0 (CC-120, migration 0016). Areas gain a "Domain" relation, two-way with Domains "Areas", **set to "Limit: 1 page"** by hand (migration 0013; T7: it can be set by hand; T8: the API ignores the limit); Orgs gain "Domains". `sync plan` treats Area · Domain as a correctable brain-owned relation **only when it holds at most one value**; with two values it is the conflict `MULTIPLE_DOMAINS` and nothing is applied for that row. Domains Name, Summary and Org are correctable.

**1.5 Navigation (module on).** Home's Areas tab groups areas by Domain (a heading per Domain, then "No domain"); an area home shows its Domain; a Domain page lists its Areas and Org. Off: nothing changes.

**1.6 Build.** CC-76: the type, lint rules (`area.domain` names a `domain`; a `domain`'s `org` names an `org`; no warning for an Area without a Domain), `note new`, `sync plan`/`render`, `brain modules`, onboarding, **and the `note.schema.json` edit**. Here (additive, no reader needed): `brain.schema.json` gains `modules.domains`.

## 2. Won't Do

**2.1 Mapping.** `brain.json` `notion.tasks.wont_do_status` (string, optional; default `"Won't Do"`): the Tasks status option meaning "closed without doing it", placed in Notion's **Complete** group next to Done. The ingest and sync never set it and never read task statuses (0018: no unrestricted status sync); Ultimate Assistant reads them live, never stores them, and sets one only after the user's yes or approved Review row (0072, [assistant.md](assistant.md) §6); the contract is for the Notion space, the mapped external database and the agent's answers. Terminal and **reopenable**.

**2.2 Where it counts.**

| Surface | Rule |
|---|---|
| Due, overdue, reminders, "What's due today", Home tabs | exclude Done and Won't Do |
| Progress (Projects "Task Progress") | completed = Done; dropped = Won't Do; **active scope = total − dropped** |
| Display | `8 completed · 2 dropped`; the percentage is `completed / active scope` |
| Zero active scope | no percentage; `no active tasks` (total 0) or `0 completed · 3 dropped` (all dropped). Never 100%, never a completion claim |
| `brain query` answers about open work | dropped tasks are not open work; mentioned only when asked |
Goals and Key Results are unchanged (they do not count tasks).

## 3. Voice captures and subject summaries

**3.1 Voice/ramble template (Inbox).** Kind Capture, Brain Status **New**. Body in order: one subject `[s1] Voice note` with items under *Highlights* (why each matters), *Commitments* (explicit only), *Ideas to explore*, each item with an id and an anchor (§4.1); then a toggle *Transcript* with the raw text verbatim. **Selection applies to a voice capture like any other input** (§4). Only the user sets **Ready**. Creating the summary never authorizes a Task.

**3.2 Recording.** T1 verified that Notion's own recording puts a readable transcript on the page and an agent can read it. Whether a recording can be **started from a template or button** was not tested and is not assumed. Supported either way: the user pastes a transcript, or a file is dropped. Guide fallback: "Record with your phone or Notion, paste the transcript into the Transcript toggle."

**3.3 Minutes format (amends 0043's eleven-heading prompt; groups from decision 0067).** `Highlights`, `Quick follow-ups`, `Tasks`, then one `## <Subject>` section per substantive subject. Inside a subject, in this order, the sub-headings that apply: *Highlights* (why it matters), *Decisions* (an agreement), *Quick follow-ups* and *Tasks* (the owner's own actions, §4.1), *Other commitments*, *Open questions*, *Concerns raised* (supported by the conversation only). Minutes written before 0067 have one *My actions* group instead of the two; they are read exactly as before. Omit empty ones; never repeat a sentence in the overview and a subject; never invent a risk; uncertain owner or inferred meaning is written "needs clarification". Substantive context and source references stay. Every item line follows the grammar of §4.1.

**Lean minutes (decision 0079, from 0.14.0; the prompt is CC-197's).** The minutes have a **readable part**, written for the user, and a collapsed toggle **For the brain**, written for the ingest. Each item's text is written once, on its readable line; the toggle holds only its quotes. What a meeting puts in Git does not change (0079 §1): only the selected transcript paragraphs (§4.5); the readable text decides what enters and what the notes say, and is never stored. The readable part, in this order:
1. **In one line:** one sentence on what the meeting was about and what came out of it. It is not an item: no id, never imported.
2. **Quick follow-ups:** the owner's to-do checkboxes (0067's 15-minute test), each ending with its follow-up id tag `[q1]`, `[q2]`, … An unticked one becomes a Task at the read that ingests the meeting (§6.3).
3. **Tasks for the brain:** the owner's explicit commitments that the ingest turns into Tasks, one item line each, ending with its item id tag (`[s2.i2]`: the id of the subject it was discussed in, or `[s0.iN]` when it belongs to none), each followed by its Scope toggle (0067, unchanged).
4. **One block per subject,** in the order discussed: a heading ending with the subject's id tag (`## Pricing [s2]`), then a gist sentence of about 25 words at most with its own item id tag, then only the lines that apply, each starting with one prefix and ending with its id tag: `Decided:` (an agreement), `Open:` (what a later meeting or document can answer), `Concern:` (a risk the conversation supports), `Waiting on <name>:` (someone else's commitment), `Idea:` (a tentative idea, only when it matters). No sub-headings inside a subject; about 15 words a line and about 5 lines a subject at most; minor topics merge into one subject titled `Other`. A subject with nothing decided or left open has its gist line only.

The **For the brain** toggle holds, in this order: the `Attendees:` and `Projects:` lines (one plain line each, the content of the two sections above), the sentence "All subjects included unless marked Meeting only. Mark Reviewed to confirm.", then, per subject in page order, its Selection line (`[s2] Selection: Use in brain`) followed by the **quote entries** of its items: `[s2.i3] “<quote>” “<quote>”`, one to three quotes under the quote rule of §4.1, with `(depends on [s1])` at the end when it applies. The quote entries of `s0` items (Tasks for the brain that belong to no subject) come first, before the first Selection line; every quote entry is joined by its id (§4.1), so its place in the toggle is the generator's rule, not read. `Meeting only` and `Use in brain` are marked here, never on a readable line; `Track: Waiting On —` is marked on the readable line (§4.1, "The lean shape").

The word and line limits are the generator's rules: the CLI counts neither words nor lines, and a long line is read exactly like a short one (Brain Assistant's Check minutes may point it out, CC-197). How each line is read is §4.1 ("The lean shape"); minutes in the 0067 shape above, minutes from before it, and the voice format (§3.1) are read exactly as before (§4.1, "Shapes").

**Migration 0023, text only.** The lean shape changes no database, property, view or button: the summary is Notion AI's text, and follow-up Tasks carry no marker. What changes is the prompt (notion/minutes-format.md and the paste guide, CC-197; since CC-258 it runs in the Notion AI chat on the meeting page, §3.4), Brain Assistant's Check minutes (notion/brain-assistant.md, CC-197), and the gray line under the notice in the Meetings default template, which says where `Meeting only` goes in the lean shape (CC-197). Existing spaces take all three with migration 0023 (notion/migrations/0023-lean-minutes.md); the published Notion template (U-27, 0078 §1) is built with them.

**3.4 Where the transcript and the minutes are on a meeting page (0.14.0, CC-258).** This section says where on a meeting page the minutes and the transcript are read. It changes nothing in 0079's format or in what enters the brain. CC-193's release gate found that running the prompt from Notion AI's settings didn't work: Notion AI replaced the transcript with the minutes. It also found that a page can end up with minutes and no transcript.
- **The transcript stays on the page.** It is in one of two places. When Notion recorded the meeting, it is the **Transcript of the page's meeting-notes block**, which the meeting's transcript tool reads. When the user pastes a transcript, it is **the page body above the minutes**, outside the meeting-notes block, the template's callouts and the My notes toggle. The minutes never replace it.
- **The minutes prompt runs in the Notion AI chat on the meeting page.** The user pastes the prompt (notion/minutes-format.md) followed by the line **"Write the minutes on this page, below the transcript, and nothing else."** This replaces "paste it once into Notion AI's settings" (migration 0023 below). The minutes then land in the page body.
- **Which minutes are read:** if the page body, outside the meeting-notes block, holds minutes in the format (an id tag such as `[s1.i1]` or `[q1]`, escaped or not, or a For the brain toggle), those are the minutes, even when a meeting-notes block with its own summary is on the page. In every other case the minutes are read exactly as before (the block's own summary, or the body when there is no block).
- **Which transcript is read:** the Transcript of the meeting-notes block when it has one. Otherwise, the page-body text above the minutes, without the template's parts. When the minutes are in the format and there is no transcript in either place, the input has a pre-check blocker of the skill (no transcript; not a CLI code, the CLI never reads Notion) and nothing is ingested. Attended and unattended alike, the meeting stays Reviewed, and the report's Needs you line names it with the fix: "<meeting>: it has minutes but no transcript. Put the transcript back on the page above the minutes: restore an earlier version from Notion's version history, or paste it again. Keep the minutes, then run catch-up again. Next time, run the minutes prompt in the Notion AI chat on the page and add: Write the minutes on this page, below the transcript, and nothing else." Minutes with no id and no toggle (a legacy summary) are stored whole as before and need no transcript.
- Setup's minutes check (spec/setup.md §6.3) checks the same thing on its sample page, with the reason `transcript-missing`.

## 4. Selection of what enters the brain

**4.1 Item grammar and identities (normative).** The summary generator (the Notion AI minutes/voice prompt, written in CC-80) writes every subject heading as `[s2] <Subject>` and every item as one line:

```
[s2.i3] (Meeting only:|Use in brain:)? (Track: Waiting On —)? <text> “<anchor quote>”{1,3} (depends on [s1])?
```

Ids are visible, unique in the page, written once by the generator and never rewritten by it; a **regenerated** summary that cannot reuse an item's id (same anchor) gives it a new one, and the old selection for it is stale (§4.6). Each anchor is a **verbatim quote of at most 12 words from the transcript**; an item carries one to three, so support that spans paragraphs cites each. That is the generator's rule; what the CLI does with a quote that breaks it is §4.2 (decision 0067: only an excluded item's quote can block).

**Quick follow-ups and Tasks (normative, decision 0067).** The owner's own actions are written in two groups, each introduced by a **group line**: a line whose text, once heading marks (`#`), emphasis and a trailing colon are removed, is exactly `Quick follow-ups` or `Tasks` (case-insensitive; `Quick follow ups` is the same). A group ends at the next heading line (one that starts with `#`), the next subject heading, the next group line, or a **section line**: a line that reads, the same way, as another section name of the format (`Highlights`, `Decisions`, `Other commitments`, `Open questions`, `Concerns raised`, `Attendees`, `Projects`, or the voice template's `Commitments` and `Ideas to explore`), so a bold label such as `**Other commitments**` ends it too. A group line or section line may carry a parenthesised hint (`Highlights (why it matters)`). Minutes written before 0067 have one group line `My actions` instead; it opens no group and its items are read as before.
- **A quick follow-up** is a Notion to-do checkbox (`- [ ] <text>`, `- [x] <text>` once ticked) with no id and no quote. **Every list line inside a Quick follow-ups group is a quick line**: a to-do, a bullet, or a line that carries an id (an item the user moved there); a Scope toggle inside the group is ignored. A quick line never becomes a Task (except a follow-up of the lean shape, below and §6.3) and nothing from it is imported. A to-do or bullet with no id is not an item: it is not selected or excluded, has no anchors, is not in the extract's `selection` and is not a blocker (`UNNUMBERED_LINE`), **except** when its text is shaped like a control (§4.3: it starts with a token phrase or `Selection`, holds one in brackets, or mixes scripts, e.g. `- [ ] Selection: Meeting only`): then it is `SELECTION_UNREADABLE`, fail closed, never skipped. `extract-plan` lists every quick line in `quick` (`{ subject, id, text, done }`, `id` when the line carried one). **Fail closed:** a quick line that carries an id is still read like an item (its token, its subject's selection, its anchors, the control checks and the subject and duplicate-id checks): when its effective selection (§4.3) is `meeting only` it is an **excluded item** in the plan (in `selection`, its anchors placed by rule 4 of §4.2 and its paragraphs kept out by the copy rule), so dragging an excluded line into Quick follow-ups never releases its paragraphs; when it is `use`, it is in no mapping. An item that `depends on` a quick line depends on excluded context (§4.7: a quick line stays in Notion, outside the brain). A `Selection:` line, a subject heading and any other line inside the group are read as usual. A to-do or bullet **outside** a Quick follow-ups group is an unnumbered line, as before.
- **A task** is an item line in the form above under a Tasks group, followed by a **Scope** toggle. A to-do marker before the id (`- [ ] [s1.i3] …`) is formatting, like a bullet.

**Open questions and Concerns raised (decision 0071).** These sections are a hint, like every heading: an item is read by what it says (§6.1), so a to-do written under Open questions is a commitment, not a question, and a concern is a risk. The minutes prompt (notion/minutes-format.md) asks the generator to put only what something can answer later under Open questions, and every action under Quick follow-ups, Tasks or Other commitments; the ingest does not rely on it.

**The Scope toggle (normative, decision 0067).** A toggle whose summary is `Scope` (`<details><summary>Scope</summary> … </details>`, the toggle form of cli §5.14.7; case and emphasis ignored, and `&lt;` `&gt;` read as `<` `>`) belongs to the **item line directly above it**: the nearest item line before it, with no other item line, heading, group line or subject heading between them. Its lines are fields: a line that starts with `Done when:`, `Due:`, `Project:` or `Notes:` (case-insensitive; a list marker before it and emphasis around the name are ignored) starts that field, and any other line continues the field above it (joined with a line break, its list marker dropped). **Due** is one line: a line that would continue it is a problem. A value that is empty, `none`, `n/a`, `-` or `—` is absent. **Due** must be a date `YYYY-MM-DD` that exists in the calendar. Nothing inside a Scope is an item, an unnumbered line or a control; a closing tag at the end of a content line closes the toggle. **Fail closed:** a heading line, a subject heading or a `Selection:` line ends any Scope and is read as usual, so a Scope never hides a subject or its selection; an item line inside a Scope is `SELECTION_UNREADABLE` (a line with an id that is not an item, §4.3). A Scope that is never closed (no `</details>` further down) also ends at an item line, a group or section line, or a list line that is not a field, each read as usual, so a missing `</details>` cannot hide an item or an unnumbered line. `extract-plan` returns `scopes`: `[{ item, done_when, due, project, notes, problems }]`, one per Scope toggle outside a Quick follow-ups group. Its `problems` (plain sentences) are: text before the first field, a field given twice (the first value is kept), a Due that is not such a date, a second Scope for the same item, and a Scope with no item line directly above it (then `item` is null). **A Scope problem never blocks the input**: it holds back only that item's Task (§6). How the ingest uses a Scope is §6.

**Shapes (normative, decision 0079).** Before any line is read, the summary's shape is decided from the whole text, folded as in §4.3:
1. **Lean** when it holds a **For the brain toggle**: a toggle (`<details><summary>…</summary> … </details>`, read as the Scope toggle is) whose summary is `For the brain` (case, emphasis and a trailing colon ignored). A line that reads `For the brain` once heading marks, emphasis and a trailing colon are removed, but is not a toggle's summary, also makes the shape lean, and is `SELECTION_UNREADABLE` itself: the toggle is the only form read, so a quote list outside one is never taken for readable lines (fail closed). CC-197's prompt gate records the form Notion AI writes; reading another form is a change to this contract first.
2. Otherwise **inline-quote** when it holds a subject or item id (`[s1]`, `[s1.i1]`) anywhere: the grammar above, which covers the 0055 and 0067 minutes, minutes from before 0067 and the voice format (§3.1). It is read **exactly as before 0.14.0**: no rule of "The lean shape" applies, a `Tasks for the brain` line is not a group line, and `[q1]` is plain text.
3. Otherwise **legacy**: no id anywhere. The ingest stores it whole, as before (the brain-ingest skill's legacy flow); `extract-plan` is not run on it.

The shape belongs to one read: a page regenerated in another shape is read in that shape at the next read the user asks for (§4.8).

**The lean shape (normative, decision 0079).** The layout is §3.3's. Each line is folded and its surrounding formatting removed as in §4.3, and toggle tags are put on lines of their own as for the Scope toggle. The **readable part** is every line outside the For the brain toggle.

*Id tags.* An id tag is an id in square brackets: a subject tag `[s2]` or an item tag `[s2.i3]` (the ids of the grammar above), or a follow-up tag `[q1]` (`q` and one or more digits, read case-insensitively and reported in lower case). A tag is read at the **start** of a line's text (after any list or to-do marker) or at its **end**; emphasis or inline-code marks directly around it are ignored (`` `[s2.i3]` ``, `*[q1]*`). A follow-up tag is a tag only on a to-do of the Quick follow-ups group; anywhere else `[q1]` is plain text. A line carries at most one subject or item tag: a second one anywhere on it, or one in the middle of its text, makes the line `SELECTION_UNREADABLE` ("a line with an id that is not an item", §4.3).

*The readable part.* Its lines are read in order:
- **In one line:** a line whose text, once heading marks and emphasis are removed, starts with `In one line` and a colon. It is not an item and is never imported.
- **Group lines:** `Quick follow-ups` and `Tasks for the brain` (or `Tasks`), read as the group lines above (heading marks, emphasis, a trailing colon and a parenthesised hint ignored). A group ends as above, and also at an In one line line, a subject heading, or the For the brain toggle.
- **Subject heading:** a line with no list marker, with or without heading marks, whose one tag is a subject tag: `## Pricing [s2]` (the tag at the end, as the prompt writes it) or `## [s2] Pricing`. The rest of the line is the subject's title, with §4.3's control checks. It opens the subject's **block**, which runs to the next subject heading, group line, In one line line or the For the brain toggle.
- **Readable item line:** in a subject block or in the Tasks for the brain group, a line whose one tag is an item tag:

  ```
  (- |- [ ] |1. )?(Track: Waiting On — )?(Decided: |Open: |Concern: |Waiting on <name>: |Idea: )?<text> [s2.i3]
  ```

  (the tag may lead instead, as in the inline-quote grammar). `Track: Waiting On —` is read only at the start of the text, after the marker (the dash may be `—`, `–` or `-`, as the inline-quote grammar is read); a **prefix** only right after it, or at the start. Prefixes match case-insensitively with emphasis around them ignored; `<name>` is the text between `Waiting on` and the first colon. Any other word before a colon is text. A prefix is a hint, as a heading is: the line is classified by what it says (§6.1), and `Waiting on <name>:` alone never makes a Waiting On Task (§6: only `Track: Waiting On —` does). The item's **text** is the line without its marker, its Track token and its tag, the prefix kept: what the user sees and corrects. A quote written on a readable line is part of the text, never an anchor. A selection token at the start of a readable line (`Meeting only:`, `Use in brain:` or a look-alike, after the marker or after the Track token) is `SELECTION_UNREADABLE`, with the reason that it is marked in the For the brain toggle. In a subject block the item's id must name that subject (§4.3). **In the Tasks for the brain group** an item may name any subject of the page, or `s0`: its subject is the one its id names, not its place (so a subject marked `Meeting only` excludes its tasks above it too), and an id naming no subject heading of the page other than `s0` is `SELECTION_UNREADABLE`. A Scope toggle under a Tasks for the brain line belongs to it (above).
- **`Selection:` lines** belong in the toggle: one in the readable part is `SELECTION_UNREADABLE`.
- **Unnumbered lines.** Every other non-empty line of a subject block or of the Tasks for the brain group, a list line or not, is an **unnumbered line** (`UNNUMBERED_LINE`, a blocker, listed in `unnumbered`), so a readable line whose tag was lost blocks instead of silently leaving the brain. Two kinds of line are not: a heading line without a tag, which is not read, and a Scope toggle with its lines, read as above. Elsewhere in the readable part (above the first group or subject, or after a group that a heading or section line ended), a list line without an id is an unnumbered line, a line that carries a subject or item tag is `SELECTION_UNREADABLE` (a line with an id that is not an item) and other text is not read, as before.
- **Quick follow-ups group:** each line is a quick line as above (0067), with one addition: a **to-do** whose one tag is a follow-up tag is a **follow-up** with that `q` id (`- [ ] Send Ana the deck [q1]`, `- [x] …` once ticked); its text is the to-do's text without its marker and tag. A to-do with no tag, a bullet and a line with an item tag are quick lines with no follow-up id, read as above (one with an item tag fail closed). A `q` id on two to-dos of the group is `DUPLICATE_FOLLOW_UP`, not a blocker: neither becomes a Task (§6.3).

*The For the brain toggle.* It is the first toggle whose summary reads `For the brain`, and ends at its closing tag, or at the end of the summary when it is never closed. A second For the brain toggle, and any toggle opened inside it, is `SELECTION_UNREADABLE` (fail closed: a nested closing tag could end it early or hide lines). Its lines are:
- `Attendees:` and `Projects:` lines: read by the ingest skill as the minutes' Attendees and Projects (they fill an empty Meeting property as before); the CLI does not read them.
- The confirmation sentence of §4.4: not a control.
- **Selection line:** `[s2] Selection: <value>`, the value `Use in brain` or `Meeting only` (§4.3). Any other value, two Selection lines for one subject, and a Selection line naming no subject heading of the page are `SELECTION_UNREADABLE`. A subject with no Selection line is `use`.
- **Quote entry:** one line per item:

  ```
  (- )?(Meeting only: |Use in brain: )?[s2.i3]( → | -> | : | — )?(Meeting only: |Use in brain: )?“<quote>”{1,3}( (depends on [s1]))?
  ```

  The token goes first on the line or right after the id, not both; it is the item's explicit selection (§4.3). A token phrase in any other place that §4.3 reads as a control (after the quotes, in brackets), or a look-alike (`Meetng only:`), is `SELECTION_UNREADABLE`. The quotes are read as anchors under §4.1's quote rule and §4.2's tolerance (curly or straight; more than three are all used). Other text on the line is not read, apart from §4.3's control checks. Two quote entries with one id are a duplicate id (`SELECTION_UNMAPPABLE`).
- Any other line that carries a tag, or that is shaped like a control (§4.3), is `SELECTION_UNREADABLE`. Any other line (a label such as `Quotes`, a note) is not read. A list line without an id in the toggle is not an unnumbered line: the toggle holds no item text.

*The join.* Each readable item line is joined to the quote entry with the same id: the line gives the item's text, its Track token and its place; the entry gives its anchors, its explicit selection and its `depends on`. The effective selection is §4.3's: the entry's token, else the Selection line of the subject the id names, else `use`. Then:
- **A readable line with no quote entry** is the problem `NO_QUOTE_ENTRY` (not a blocker by itself). It is an item with no anchor, so §4.2 decides: included, it is in `quotes` with `anchor: null` and in `unplaced_items`, and is not imported (rule 3); excluded, it is `SELECTION_UNMAPPABLE`, a blocker (rule 4).
- **A quote entry with no readable line** is the problem `ORPHAN_QUOTE_ENTRY` (not a blocker by itself). It has no text, so nothing is imported from it. Fail closed, as for a quick line with an id: when its effective selection is `meeting only` it is an **excluded item** of the plan (in `selection`, its anchors placed by rule 4 and its paragraphs kept out by the copy rule), so deleting the readable line of an excluded item never releases its paragraphs; when it is `use` it is in no mapping and cites nothing. An item that `depends on` an orphan entry depends on excluded context (§4.7), as one that depends on a quick line does: the entry's item has no text and stays outside the brain.
- An id on two readable lines, or a subject tag on two headings, is a duplicate id (`SELECTION_UNMAPPABLE`), as before.

From the join on, everything is as for the grammar above: §4.2's placement and copy rule, §4.3's controls, §4.4 to §4.8, the Scope toggle and the quick lines. **Each item's text is read from its readable line** as the page holds it at the read: a line the user corrected is the text the brain reads (the extract still stores only the selected paragraphs, §4.5).

**4.2 Passage mapping (the CLI/skill computes it; no AI-authored numbers).** The transcript (or minutes text) is stored verbatim and its paragraphs are numbered `¶1…¶n` when the row is first read, with a `transcript_hash`. An item's passages = the paragraphs where its anchors are **placed**, by **exact substring match after whitespace normalization** (decision 0067 amends the rest of this rule):
1. **Exact.** An anchor that occurs in exactly one paragraph is placed there, **whatever its length** (a quote longer than twelve words that occurs once is used as it is).
2. **Stretch (included items only).** An anchor that occurs in **no** paragraph (reworded, or two sentences joined) is looked at in stretches of consecutive words: for L from 12 (or the anchor's word count, if fewer) down to 6, the stretches of L words of the anchor that occur in exactly one paragraph. The first such stretch at the greatest L (the leftmost, if several) is used; then the words of the anchor left before it and after it are each treated the same way, while 6 or more remain, so a quote that joins two sentences is placed in both their paragraphs. The anchor is placed in the paragraphs of the stretches used, and `quotes` lists it with `result: "shortened"` and those stretches. With no stretch of 6 or more words that occurs in exactly one paragraph, it is not placed. An anchor that occurs in **several** paragraphs (identical or overlapping text recurring) is not placed; no stretch of it is tried.
3. **Included item: reported, not a blocker.** For an item whose effective selection (§4.3) is `use`, an anchor that is not placed is listed in `quotes` with `result: "unplaced"` and its reason; the item keeps the anchors that were placed. An included item with **no** placed anchor (none placed, or none written) has no passage: it is **not imported** (nothing is written from it, no Task) and is listed in `unplaced_items`. More than three anchors are all used. None of this makes `ok` false; the attended run offers the repair (below), and the report names the items so the user can fix the page.
4. **Excluded item: a blocker, as before.** For an item whose effective selection is `meeting only`, only rule 1 counts: an anchor that is not placed exactly, or an item with no anchor, is `SELECTION_UNMAPPABLE` and blocks the input, because the brain must know every paragraph an excluded item rests on to keep it out of Git (fail closed). The generator or the repair step (§9.3) must extend the quote until it is unique. **Parser tolerance (observed in T6, normative for CC-78).** An item's quotes may be curly “…” or straight "…"; a list marker, bold marks or a bullet before the id are ignored (T2 showed paragraphs becoming bullets). A list-item line **without an id** is an **unnumbered line**. It can neither be selected nor excluded and has no anchors, so it could not take part in the fail-closed collision check below: an unnumbered line is therefore a **blocker for the input** (`UNNUMBERED_LINE`), attended or unattended, until it has an id, a selection and anchors. In an attended run the repair step proposes the id and anchors and the user confirms them in the preview; an unattended run skips the input and names the line under Needs you. The plan and the preview list every unnumbered line. Nothing from it is ever imported or copied by itself. Owner Tasks come from numbered items only (§6). **Subjects have no passages of their own**: a subject acts only through its items. `depends on [x]` must name an existing id; a missing id, or a cycle among items, makes the items concerned `SELECTION_UNMAPPABLE`. Any unmappable item is a blocker for the input (never a snapshot of the whole transcript); in an attended run the skill offers a **repair**: it proposes new anchors for those items, quoted from the transcript, and the user confirms them in the preview. It offers the same repair for an included item's `unplaced` quotes and `unplaced_items`, which do not block: the user may also go on without it.

**Passage identity.** A passage is `(extract_of, transcript_hash, ¶n)`. The transcript is immutable once its hash is recorded, so `¶n` is stable; **two identical paragraphs are two passages** (different `¶n`). The `passage_hash` kept beside it is a check, not the identity.

**What the mapping proves, and does not.** It proves the cited text exists and where. Whether an item faithfully says what its anchors support is what the user reads in the preview (§4.4, §7): a stated limit. A paragraph is the unit: a selected item pulls its whole paragraph, other sentences in it included; the preview shows the **full text** of each paragraph it will copy (§4.2, §4.4).

**Which paragraphs enter the extract (normative).** For each paragraph take the effective selection of **every** item that cites it (§4.3: its own token, else its subject's, else `use`). **If the citing items all say `use`, the paragraph is copied. If they all say `meeting only`, it is not. If they disagree, it is not copied (fail closed)**, whatever the weights of their tokens: copying it would carry the excluded item's words into Git. An item with a `use` selection whose paragraph is not copied for that reason becomes `SELECTION_UNMAPPABLE` ("shares a paragraph with excluded content"), and the §4.2 repair step proposes tighter anchors that cite a different paragraph; if the shared words cannot be separated at paragraph granularity, the input stays a blocker and the user is told which two items collide. So an explicit `Use in brain:` item under a `Meeting only` subject enters the extract only when no excluded item cites its paragraph, and a paragraph shared by items of two subjects, one excluded, is not copied. Items listed "its evidence is excluded" are not imported (as §4.7). A paragraph cited by **no** item is not in the extract; the preview lists "n paragraphs are covered by no item", and the repair step can add an item for them.

**Preview shows what is copied.** The §4.4 preview lists, for every paragraph that will be copied, its **full text** (not first and last words), with the items that cite it. **Decided by the user (2026-11-01): paragraph granularity with the fail-closed rule above.** How often paragraphs collide is measured in the acceptance run of selection and Review (U-23, tracked in the Notion test task); if collisions are frequent, a sentence-level extract or an explicit per-case override in the attended preview (the user may then copy a mixed paragraph, knowing it holds excluded words; only the user can authorize that) is a follow-up, not part of 0.8.0.

**4.3 Controls and effective selection.** Subject: the line under the heading reads `Selection: Use in brain`; the user types `Selection: Meeting only` (planned mechanism M1, §9). Item: the optional prefix of §4.1. Tokens match case-insensitively and exactly; anything else is `SELECTION_UNREADABLE`, a blocker for that input, including an item prefix that is close to a token (`Meetng only:`, `Private:`): it is never read as inherited inclusion. The same holds for any other spelling of a control: a token phrase (`Meeting only`, `Use in brain`) at the start of an item's text or a subject's title, or inside brackets or parentheses, outside the exact forms (the same words in the middle of a sentence are prose and do not block), a word that mixes Latin letters with Cyrillic or Greek ones (a look-alike spelling), a `Selection` line that does not parse, two `Selection` lines for one subject, and a line that carries an id (`[s1.i2]`) but is not an item. Before reading, each line is folded with Unicode NFKC and zero-width and other format characters are removed (so `Meeting\u200b only` and a full-width colon read as written). **Markdown escapes (0.14.0, CC-229):** after that, a backslash before an ASCII punctuation character is removed and the character kept, as Markdown reads it (`\[s1.i1\]` is `[s1.i1]`, `\*` is `*`, `\"` is `"`, `\\` is one backslash; a backslash before a letter, a digit, a space or any other character stays). The Notion API's markdown export escapes every bracket of the minutes (`\[s1\]`, `\[q1\]`), so without this fold its ids, tags and quotes would not be read; with it, minutes read through any path are read as the page holds them, and minutes with no escape read exactly as before. The shape ("Shapes" above) is decided after this fold. The transcript is not folded: it is stored and matched as written (§4.2). Formatting around a line is ignored (blockquote `>`, emphasis around the whole line), the `Selection:` line may follow other lines of its subject, and the confirmation notice of §4.4 is not a control, whether it carries a callout icon, sits in a callout or quote, or is wrapped over lines. An item belongs to the subject its id names (`[s2.i1]` is s2's): placed under another subject, or before its own heading, it blocks (visible: the input is listed under Needs you with the line); the lean shape's Tasks for the brain group is the one exception (§4.1). **Effective item selection** = the item's explicit token, else its subject's, else `use`.

| Subject | Item token | Effective |
|---|---|---|
| untouched (`Use in brain`) | none | use (all included unless marked) |
| `Meeting only` | none | **meeting only** (a subject exclusion excludes its contents) |
| `Meeting only` | `Use in brain:` | use (the explicit individual exception) |
| `Use in brain` | `Meeting only:` | meeting only |
| item outside any subject (overview Highlights, Tasks, or My actions before 0067) | none | use (U-default); if its paragraph is not copied under the §4.2 rule (all citers `use`) it is dropped |

**4.4 Confirmation.** Every unprocessed summary says: **All subjects included unless marked Meeting only. Mark Reviewed to confirm.** (Inbox: Ready.) Reviewed/Ready **confirms the visible selections as the first run that sees the status reads them** and nothing else. New/Not Reviewed is **unconfirmed**: never ingested. The assistant may *suggest* `Meeting only` for small talk only by writing the token for the user to see; an unfamiliar substantive subject stays `use`. Binding (decision 0058's analogy): Reviewed/Ready has no timestamp, so the confirmation is the page as **read by the first run that sees it Reviewed/Ready**; an **attended** run shows the user each subject and item with its effective selection and the **full text of every paragraph it will copy** (§4.2), and imports after a yes; an **unattended** run imports a confirmed input only when the page's `last_edited_time` is at least 2 minutes older than the run (so the page has settled), reads the tokens as they are, and states in its report that an edit in the confirming minute cannot be detected. It never turns an unconfirmed input into Reviewed/Ready (0051).

**4.5 The selected extract (source).** A selected input becomes a source with `extract: true` (CC-78 adds the fields to schema §4): body = the **selected paragraphs only, as written** (line breaks kept; only matching and hashing normalize whitespace), in transcript order, each preceded by `<!-- passage ¶a item s2.i3 -->`; frontmatter `extract_of` (the Notion page id of the full input; the full text stays in Notion untouched), `extract_version` (1, 2, …), `transcript_hash`, `selection` (`[{id, effective, explicit}]` for every subject and item), for each included paragraph its `¶n` and `passage_hash` (the first 8 hex of the sha256 of its normalized text, as a check). **Never** the full transcript. A passage is identified across versions by `(extract_of, transcript_hash, ¶n)` (§4.2).

**4.6 Cases (normative).**

| Case | Result |
|---|---|
| Untouched defaults, confirmed | every cited paragraph included; extract v1 |
| Parent override | items excluded unless an item has an explicit `use` |
| Item override | only that item |
| Unconfirmed | blocker `UNCONFIRMED`; not ingested; unattended: Needs you |
| Selection changed before ingestion | the confirmed selection read is the one used |
| Selection changed **after** ingestion (the user edits the tokens and sets Reviewed/Ready again, §4.8) | the explicit re-read finds it; a new extract version `replaces` the old one (schema §4 versions); paragraphs in the old and not in the new are **suppressed** (§5); paragraphs only in the new are new input |
| Re-inclusion (`Meeting only` back to `use`) | a new version containing it; the paragraph is `re-included`; claims that cited it stay restricted until the user accepts their **Restore** item (§5.1) or they are proposed anew |
| Transcript changed on an explicit re-read (`transcript_hash` differs) | a new version with the new mapping; **every paragraph of the old version is suppressed** (a passage is identified by `(extract_of, transcript_hash, ¶n)`, so none of them carries over), and claims resting on them wait for the cleanup row (§5); attended: preview first; unattended: skipped, Needs you |
| Unmappable (an excluded item's anchor missing or ambiguous), unreadable token | `SELECTION_UNMAPPABLE`/`SELECTION_UNREADABLE`: a blocker for that input; **never a snapshot of the whole transcript** |

| Lean shape: a quote entry with no readable line (`ORPHAN_QUOTE_ENTRY`) | not a blocker by itself: nothing imported from it; when effectively `meeting only` it is an excluded item, so its paragraphs stay out |
| Lean shape: an unticked follow-up with a `q` id | not a blocker; a Task at the read that ingests the input, once per `q` id (§6.3) |
| Lean shape: a ticked or deleted follow-up, or one whose `q` id is on two to-dos (`DUPLICATE_FOLLOW_UP`) | no Task; not a blocker |
| Lean shape: a selection token on a readable line, a `Selection:` line outside the toggle, a nested or second For the brain toggle | `SELECTION_UNREADABLE`: a blocker |
| Inline-quote or legacy shape | read exactly as before 0.14.0; follow-ups never become Tasks (§6.3) |
| Same selection read again | `DUPLICATE_SOURCE` (cli §5.5) |

**4.7 Shared context.** An item may carry `(depends on [s1])`. If an item is effectively selected and what it depends on is effectively excluded, the item is **not imported** and is listed "depends on excluded context", **unless it has an explicit `use` token**: then only its own passages are imported, and every claim written from it carries `context_excluded: true` (shown in Review, so the user sees it stands alone). There is no judgment step: the CLI checks ids only and reports `DEPENDS_ON_EXCLUDED`. **The chain is followed:** an item that depends on an item which itself depends (however far back) on excluded context is excluded context too, and is not imported unless it has its own explicit `use` token.

**4.8 Selection changes after ingestion are explicit (decision 0062).** The catch-up does **not** read an ingested page again to look for changes: Notion's page time does not move on a deletion (T4), and reading every page costs tokens and still misses cases. A selection changes only when the user says so: they edit the tokens and set the meeting back to Reviewed (the Inbox row back to Ready), as for any corrected input (0045), or they ask the assistant. The next run then reads the page as a new version of the input, runs `brain source extract-plan --previous <latest extract>` (cli §5.22) and compares **passages**, which is all the stored extract needs to hold:
1. `transcript_hash` differs → no passage identity carries over: the new version holds the new mapping and **all** paragraphs of the old version are suppressed (fail closed). Attended: the §4.4 preview first. Unattended: skipped and named under Needs you, because it suppresses everything.
2. Same `transcript_hash` and **`write_required`** (cli §5.22: a paragraph is `suppressed` or `added`, or the item ids or their passages differ from the stored `selection`/`passages`) → `suppressed` = paragraphs in the old version and not in the new plan, `added` = paragraphs only in the new one. Attended: the preview of §4.4, then a new version. Unattended: only when the page's `last_edited_time` is at least 2 minutes older than the run (the edit-minute limit of decision 0058 is stated in the report); then the new version is written (an addition) and the restriction of §5 applies at once, with the regenerated views, in one operation; otherwise it waits (`TOO_FRESH`). `selection_changes` (item ids whose effective selection moved, from the stored `selection`) are shown in the preview and are not needed for the comparison.
3. Same `transcript_hash` and **not** `write_required` (no paragraph differs and the item ids and passages per item match the stored ones) → no new extract version (`UNCHANGED`). A mapping-only difference (a regenerated summary gave an item a new id, paragraphs unchanged) is covered by step 2: a **new version is written** with the same body, the current `selection`, `passages` and item mapping, and **no** suppression record (nothing is suppressed).
4. **After the version decision, in every branch where the input is not blocked or skipped (steps 1 to 3, attended and unattended; an unattended run that waits with `TOO_FRESH` or skips for Needs you does not reach it).** The current validated selection is persisted by the version of step 2, so Task creation and `sync record` validate against it. Order: the version, if any, is written first, then the comparison below, then any Task is created and recorded. A re-ingest request **runs the ordinary ingest comparison** on the selected paragraphs (cli §6, ingest): the claims it would write, including those from corrected summary or item wording (the extract stores paragraphs, not item text), are matched against existing knowledge and conflicts, corrections and duplicates become Review items; nothing is duplicated. **Path and idempotence.** The ingest does not call `note new` for the source (that would stop at `DUPLICATE_SOURCE`, cli §5.5): it takes the existing latest extract as the source and matches its paragraphs and the corrected wording against existing knowledge. It proposes only changes with no pending or decided proposal for the same target and content already (`brain proposal list`), so a second run, attended or unattended, finds nothing new. **Tasks are idempotent per item.** A Task is tied to the item that authorized it: `sync record` stores `task_items` (`{<item id>: <Notion task page id>}`) beside `tasks` on the extract source. `brain source extract` carries `task_items` forward to each new version, and the lookup also covers every source along the `replaces` chain, so a later version never loses a mapping. A re-ingest creates a Task only for an item that now carries an explicit owner commitment or `Track: Waiting On` (§6), **has no entry in the union of `task_items` along the chain, and only when `legacy_tasks` is empty**, and records it (`sync record` `task_items`, cli §5.14.6); an item that already has a Task never gets a second one, and nothing is cancelled or deleted. So a user who adds `Track: Waiting On` to an item gets exactly one Task, and repeated attended or unattended runs create none more. **An item the brain already holds as a question is not reclassified (decision 0071, §6.1):** when a question note raised in this meeting (or citing this input) already says what the item says, open, answered or dropped, the re-ingest creates no Task for it, even if the item now reads as the owner's to-do; only the to-do tidy (§6.2) converts it. An item whose wording the user corrected is a corrected line: it gets its Task once, as above, unless the question it corrects was dropped with a `task` (that Task stands), and the old question is named under Check to drop. **Legacy and unmappable Tasks (conservative).** A Task is **mapped** only when a `task_items` entry binds it to an item id that exists in the **current** plan; the Tasks of the chain (`tasks`) that are not mapped (a full copy made them, or the item id disappeared when the summary was regenerated, so the item now has a new id) cannot be tied to an item (`legacy_tasks`, cli §5.22). While there are any, a re-ingest creates **no** Task automatically: the item is listed as "possible Task" with the links of the existing Tasks, an attended run creates it only after the user confirms, and an unattended run skips it and names it under Needs you. The cleanup row (§5.2) lists the Tasks of an earlier full copy too. (If a run stops between creating a Task and recording it, a retry can create it twice; this is the existing limit of cli §5.14.5.) The row returns to its ingested status when the run ends, so the request is consumed once.
**A retry** after a failed write starts again from the same latest version, so it computes the same result; a new version is written once.
**Re-ingest to check consistency.** Setting a document or meeting back to Reviewed/Ready is also how the user asks the brain to look for inconsistencies: the ordinary ingest comparison runs against what the brain already holds (a changed version also through `source diff`, 0045) and conflicts become Review items. Detecting a deletion in Notion without such a request is not part of 0.8.0 (decision 0062; a possible future exploration).
Deleting a block or a line without setting the meeting back to Reviewed is **not a request**: the brain keeps what it has, and the docs say so.
**Failure and retry.** `brain source extract` (cli §5.23) writes the new version, its suppressed-passage record and the regenerated views as one journaled operation. They are staged in the workspace checkpoint (`workspace.checkpoint()` / `restore()`, as `sync apply` does) and flushed and committed once; if any part fails the checkpoint is restored, nothing is committed, and the next run starts again from step 1 against the same latest version. The checkpoint only restores in-memory staging, so a **crash** between file writes needs its own protocol (§7.11, **write-ahead journal and recovery**): the guarantee is fail-closed recovery, not atomicity of the disk writes. A single user on a local disk is assumed for concurrent readers.

## 5. Exclusion after ingestion: what it affects and how it reconciles

**5.1 Passage references and eligible evidence (normative).** Every claim written from an extract carries a **passage reference** `src-…#¶n:<passage_hash>`: in a timeline entry the field `passage`; in a note body a marker `^[src-…#¶n:<hash>]` after the statement (a provenance marker beside §9's, required by lint on statements derived from an `extract` source). A timeline entry rests on a passage when it carries the field `passage`, and a fact is eligible only while one of its accepted timeline entries is live. **Eligibility algorithm (normative).** For a claim, take its provenance entries (`source`/`sources`, a timeline `source`, passage references). **An entry that names no source or meeting has no input lineage and is live** (CC-174): the id of a knowledge note or memory (`dec-…`, `prj-…`, `mem-…`), an agent session key `agent:<agent>/<session>` (what a memory written in a session may cite), and a timeline's `notion-edit` or `user-correction:<prp id>` name no input that a suppression can change, so they never restrict a claim, whatever is suppressed elsewhere in the brain. (Whether a memory whose cited notes are all left out is still supported is [memory.md](memory.md) §2 rule 4's question, not lineage.) For every other entry, one that names a source or meeting, find its **input lineage**: the input (Notion page) it came from, through `extract_of`, the `replaces` chain, or the source's `source_key`; a source key `notion:<page id>`, `url:…` or `file:…` written in place of an id is its own input. An entry naming a source or meeting whose lineage **cannot be determined** (a source with no `source_key`, no `extract_of` and no `replaces` link to one that has them, a meeting with no `source`: a data defect, reported by lint as `unknown-lineage`, cli.md §5.10; or a `src-`/`mtg-` id that names no note, lint's `missing-ref`) is **never live while any suppression is active in the brain** (§5.3), whether or not a changed input appears elsewhere in the claim (fail closed). It is released **only** by one of two events: (a) the lineage is established (the defect is fixed, e.g. a `source_key` is added, after which the normal rules apply), or (b) the user explicitly marks the note independent in the cleanup row (**Keep** on its "Is this note independent of <input>?" item), recorded on the note as `lineage_cleared: [<input id>, …]`, a **list**, one entry per input, so a second Keep adds to it and never replaces the first. Deciding or rejecting the cleanup row does **not** release it. Let C be the inputs that have a changed (suppressing) extract version. Then an entry is **live** if (a) its lineage is not in C, or (b) it is an extract passage `(extract_of, transcript_hash, ¶n)` present in the **latest** version of its input **and** not a re-included passage awaiting Restore (§5.2). **A claim is eligible if it has at least one live entry; otherwise it is restricted.** So a claim resting on a suppressed passage and on the same meeting's older full copy has no live entry (both are in C); a claim that also cites a different input is eligible; a re-included passage becomes live when its Restore item is accepted.

**From 0.13.0 (0077):** how this algorithm reaches every read, metadata, derived content and a proposal's passages, and which item is withheld whole, is [eligibility.md](eligibility.md); where the table below differs, that file wins (its §13).

**A note with nothing eligible left is restricted whole (normative, CC-174).** A knowledge note or memory with a restricted claim (a blanked body line, a dropped timeline entry) and nothing eligible left is restricted whole for retrieval and the derived views, rather than returned as a title with every claim blanked. Nothing eligible is left when all three hold: no body line outside the restricted lines has content (blank lines, headings and comments are not content), its `summary` is dropped (as it is for every partly restricted note), and no fact is live. `brain query`, `brain recall`, `brain reflect`, Review pages and the derived views leave it out. It is not a lineage defect: its cleanup item is still the removal or correction of its restricted claims (§5.2), `brain status` does not count it as unresolved lineage, and the index and Notion keep it listed, by type and id in the awaiting-cleanup form (the Indexes row below; cli.md §5.8, §5.14.4).

**A reconciled cleanup frees nothing it left in place (normative).** A passage of an extract is live only while the latest version of its input holds it, whatever the status of the suppression records. A whole-source entry (an older version or a full copy) of an input that was ever suppressed is not live either, unless the note is marked independent of that input (`lineage_cleared`); a note that rests on such an input and still has body text with no passage reference stays restricted whole (once the cleanup is reconciled, headings and comments are no longer counted as text). A source note that is an older version or a full copy of an input with an extract is not returned by retrieval, whether or not its cleanup is reconciled; the text stays in Git (0032). A Restore accepted at an earlier version stands for a later version that holds the passage, until a suppression removes the passage again.
**Input lineage (normative).** The extract, its non-extract copies (a full capture of the same page, the meeting read in full) and every older version are **one input**: they count as a single source for eligibility. A claim is independently supported only by a source from a **different** input. **Text that cannot be mapped to claims** (an older note, a Document, a report line, a Brief with no passage references) fails closed: if a changed input appears anywhere in the note's lineage, the note is **restricted whole** for that input's suppression until it is resolved for that note (§5.3), **even if it also has an independent source from another input**; the cleanup row then separates what stays. A kept Document made from the changed input is restricted whole immediately. (A safe default: it can hide a note that is mostly independent until the user answers; the cleanup row says which.)
**Writing a new extract version, committing its suppression record and regenerating the derived views (`brain views`: Briefs, Decision logs, area Briefs) are one operation** (CC-78), so a derived view never shows a restricted claim and no retrieval surface sees one between the version and the cleanup.

| Surface | Rule while a claim is restricted (cleanup pending or accepted) |
|---|---|
| `brain query` answers and candidates | the claim is excluded from the answer; the answer says "restricted: awaiting cleanup" only if asked. A note body statement carrying only restricted references is not quoted or summarized |
| `brain reflect` (0.9.0) | not a signal, not evidence |
| Pending proposals resting on it | **checked before apply**: an item resting on a restricted claim, even beside a live one (a mixed item), is withheld whole: closed `stale` (reason `source_excluded`) and not applied, neither whole nor in part, even if its token is Accept; it can be proposed again from its live passages, as a new item that needs its own decision ([eligibility.md](eligibility.md) §4.2, §9.5). One without established passage support is withheld too: every change names the passages it rests on (schema §11 `passages`), and one any of whose passages is not live, or a legacy one (written before the field) whose input has a suppression record, is withheld the same way; on an older-layout row approved whole each folded change, note and link is judged alone ([eligibility.md](eligibility.md) §9). "Resting on a restricted claim or without established support" is one rule on every surface, defined in cli.md §5.7 ("Excluded evidence"): the Review page, a Review row without item sections, `brain apply` for a decision given in chat or on an older-layout row (reason `SOURCE_EXCLUDED`), `brain proposal list`, which lists such an item without its wording, and `brain proposal new`, which does not write such a proposal and refuses one with no passages (cli.md §5.6) |
| Derived views (Brief, Decision log, area Briefs) | the line is left out at the next `views` run; a note with a restricted claim is shown by type and id, with no title or link (cli.md §5.9). A view that still rests on a restricted note is withheld whole from reads and its Notion section until `brain views` rebuilds it (eligibility.md §8) |
| Reports | the report is withheld whole (cli.md §5.13.1, "Views") when it rests, directly or through another view, on a restricted note, or was written before the exclusion; the second **stays withheld after the cleanup is reconciled** until a refresh writes a new `generated_at`. Its Notion page shows a withheld notice in place of its prose until then (cli.md §5.14.4), and `brain lint` flags each line that links a restricted note (`report-source-excluded`, cli.md §5.10). Accepted report text is not edited by the brain (eligibility.md §8) |
| Documents / kept text | a Document made from the excluded passage is listed (Remove / Keep); never silently deleted |
| Tasks (Notion) | listed with their link; **never cancelled or deleted by the brain** |
| Indexes | the note stays listed (it may be independently supported), by type and id with no title, path, summary, aliases or tags while it has a restricted claim or is restricted whole (cli.md §5.8, eligibility.md §6 rule 5) |

**5.2 Reconciliation (one Review row per input; CC-78 builds the plan, CC-79 the row and its decisions).** When the user accepts a Remove or a correction for a note that stays, or a Keep, the cleanup apply writes `lineage_cleared` for that input on the note (cli §5.23): a note that still cites the input is released only that way. When a new version suppresses or re-includes passages, the next catch-up writes **one** proposal (a `review_notes` carrying a `cleanup` field, shown as the Exclusion cleanup row; its items are `remove`, `restore` and `independence`, cli §5.26, §7) whose items are: per affected note, the restricted claims with the proposed removal or correction **and beside each the independently supported claims that stay** (a claim with another eligible reference is shown as kept); per affected Task, its link and "created from excluded content" for the user to act on in Notion (found through the `tasks` and `task_items` of the earlier extract version, or the `tasks` of an earlier full copy, schema §4 source; for a full copy every Task is listed, since its items are unknown); a Task recorded under a follow-up's `q` id is never listed, §6.3; per affected Document, Remove/Keep; per **re-included** claim, **Restore**; per note with **unknown lineage**, "Is this note independent of <input>? Keep / Remove" (Keep records `lineage_cleared`, §5.1). Accepted items apply by the ordinary rules. Source versions and audit history stay (0032): an operational exclusion, not a promise to erase Git history; the Notion meeting remains intact.

**5.3 Active suppression (normative).** A **suppression** is recorded, in the same operation as the extract version (§5.1), in `_suppressions/<input id>.json`, an **append-only list of records** `{ input, records: [ … ] }` (cli §5.23): each version that suppresses something appends one record (`suppressed` not empty, or a full-copy transition); a mapping-only or addition-only version appends none; an earlier record is never removed, so a later change cannot release an earlier unresolved exclusion. A record holds the input, the version, the suppressed passages `(extract_of, transcript_hash, ¶n)`, `full_copies` (the source ids of an earlier non-extract copy of the input, when the extract first replaces one; their claims are restricted whole, §5.1) and its own `status: active`. A record is **never deleted** and its `input`, `version`, `passages` and `full_copies` are **never edited**. The one permitted change is its `status`, from `active` to `reconciled` (never back), written with `reconciled_at` by the cleanup apply; other records stay as they are. A record becomes `reconciled` only when every note it restricted is either corrected or removed through an accepted cleanup item, marked independent (`lineage_cleared`), or has its lineage established. Restrictions (§5.1) depend on **active suppressions**, not on the cleanup proposal: (1) *before the cleanup row exists* (from the version write until the next catch-up writes it) claims are already restricted; (2) *after the row is accepted or rejected* a note stays restricted until its own item is resolved as above (a rejected row leaves its notes restricted and listed as "unresolved lineage" in `brain status`); (3) *after independent provenance is established* the note is released. Unknown-lineage entries (§5.1) are not live while any suppression is active, and `brain status` counts them. **Release is per note and per active suppression.** A note is released only when, for **every** active suppression S, one of these holds: its input is in the note's `lineage_cleared`, its lineage is established as independent of S's input, or S's cleanup item for it was accepted as a removal or correction. A **new** suppression added later restricts the note again until its input is resolved too. With two active suppressions, Keep for the first leaves the note restricted by the second; a rejected cleanup row resolves nothing. The same rule governs unmapped text that is restricted by lineage (§5.1): it stays restricted until each relevant suppression is resolved for that note. CC-78's tests cover the three timings (before the cleanup row exists; after it is accepted or rejected; after independent provenance is established) and overlapping suppressions (Keep for one input only; a later suppression of a second input).

## 6. Tasks: yours by default, Waiting On explicit

Only the owner's **explicit** commitments become Tasks (cli §5.14.5). The owner is resolved with the configured identities and aliases, never a name in a prompt. Other people's commitments stay in the subject text. An item is tracked as **Waiting On** only by the token `Track: Waiting On —` in the item grammar (§4.1), after any selection prefix; `sync tasks` (CC-80 extends cli §5.14.5) then accepts an item `{ "status": "waiting_on", "owner": "<their name>" }` and renders status `Waiting On` with that name in the owner property; without the token the owner-only rule holds. Ambiguous owner, a tentative idea ("we could…") or `needs clarification` → no Task. Tasks come only from **selected** items of a **confirmed** input; an item whose anchor is excluded creates none.

**6.1 A to-do is not a question (normative, decision 0071).** Every line of an input, in any format (the item grammar of §4.1, the minutes before it, any other headings, a document, an email, a capture), is classified by **what it says**, never by the heading it sits under, with one exception: a **Quick follow-ups** line (§4.1, decision 0067) stays on the page whatever it says, never a question, and never a Task except as an unticked follow-up of the lean shape (§6.3, which does not classify it either).

| The line | Becomes | Never |
|---|---|---|
| Something a later document, meeting or answer can settle ("Is the Q3 budget confirmed?", "Who owns the mobile app?") | a **question** note (`kind: question`) when it matters beyond the input | a Task |
| A risk or concern ("the vendor may miss the deadline") | a question note with `kind: risk` | a Task |
| The owner's own **explicit** to-do ("I'll send the revised quote", "can you send me the plan" addressed to the owner) | a **Task** (§6, cli §5.14.5); with the Tasks module off, a line in the meeting's `## Action items` (or the report's list for another source) | a question |
| Someone else's commitment ("Maria will share the contract") | text: the meeting's `## Action items`; a **Waiting On** Task only when the item carries `Track: Waiting On —` (§6; the brain never adds the token) | a question |
| An ambiguous owner, `needs clarification`, or a tentative idea ("we could…", "maybe try…") | **nothing**: no Task and no question; the report names it under Check | a question, a Task |

A line someone has to act on is a commitment and never a question, even when it is phrased as one: "Can you check the invoice by Friday?" asked of the owner is the owner's to-do; "Should we check the invoice?" with no one taking it on is a tentative idea, so nothing. The table applies to the first ingest and to any later re-read; a re-read never reclassifies what the brain already holds (§4.8 step 4).

**6.2 The to-do tidy (normative, decision 0071).** A one-off, attended step of the ingest skill (never unattended, never scheduled), run when the user asks ("turn my to-do questions into tasks"). It reads the brain's questions that are `kind: question`, not `archived`, have no `answer` and no `dropped`, and whose Notion Status is Open or empty, and lists those that read, by §6.1, as:
- **the owner's to-do** → offered as **Convert**: one Task, then the question dropped with that Task. With the Tasks module off, offered as **Drop** only (nothing becomes a Task; the line stays in its meeting's text);
- **someone else's commitment** → offered as **Drop**: no Task, and never a Waiting On Task (§6: Waiting On only through the token);
- anything else is not listed.

Each item is applied only after the user's yes for it ("yes to all but 3" names each); a no leaves the question as it is, and nothing is written for an item the user did not answer. **Convert** creates the Task with `brain sync tasks --meeting <raised_in>` (no `item`), or `--source <its source>` for a question from another input. A source that is an **extract** (a selected capture) needs the `item` that authorized the Task (cli §5.14.5): it is the item of the paragraph the question cites (the `¶n` of its passage reference, whose marker `<!-- passage ¶n item … -->` in the extract names the items citing it) when exactly **one** item cites it, and the Task is then recorded with `task_items` too; with several or none, the question is offered as Drop only, saying why. A question with neither `raised_in` nor a source is offered as Drop only. The skill records the Task with `brain sync record` on that meeting or source, then runs `brain question drop` with `task` (cli §5.30); **Drop** runs `brain question drop` without `task`. A dropped question is `archived` and records `dropped` (the date) and, after a Convert, `task` (the Task's page id); the next publish sends its Lifecycle Archived and its Status **Dropped**, once (cli §5.14.4), so it leaves the open views and stays in the Archive as history. A dropped question is never listed again, and no re-ingest makes a Task from its line (§4.8 step 4). Nothing is deleted.

**Quick follow-ups and Scope (decision 0067).** A quick line (§4.1) never becomes a Task, whatever it says, except an unticked follow-up of the lean shape (§6.3). For an item that becomes a Task and has a Scope, the ingest uses the Scope as the user left it: **Due** is the Task's due date (instead of a date read from the text) and **Project** names its project, which replaces the project the ingest would infer; the skill resolves the name to a project note by title or alias. **Done when** and **Notes** become the Task page's body, in that order, each under its label; `sync tasks` (cli §5.14.5) has no body field, so the skill writes them as the page content when it creates the page. A field left empty falls back to today's rule (a date in the text, the inferred project, no body). **A Scope the ingest cannot use holds back that one Task**, never the input: a Scope with `problems`, or a Project that names no project or several. Attended, the skill shows the reason and asks (fix it on the page, or create the Task without that field); unattended, it creates no Task for that item and names it under Needs you. A Task is created once per item (§4.8): a Scope edited after its Task exists is not read again, and the Notion Task is then the place to change it.

**6.3 Quick follow-ups left unticked become Tasks (normative, decision 0079).**
- **Which.** At a read that ingests an input in the lean shape (§4.1), each **follow-up** (a to-do of the Quick follow-ups group carrying a `q` id) that is **unticked** on the page as read becomes one Notion Task: in `extract-plan`, the `quick` entries with `task: true` (cli §5.22). A ticked follow-up, one deleted from the page, one with empty text, a quick line with no `q` id, and a `q` id on two to-dos (`DUPLICATE_FOLLOW_UP`) create none. Nothing is classified: the checkboxes are the owner's own list, so §6.1 does not apply and an unticked follow-up becomes a Task whatever it says.
- **When.** Only at a read that ingests the input: its first read, or a read the user asks for by setting the meeting back to Reviewed (§4.8), in the run's Tasks step after the version decision (§4.8 step 4; also when the version is `UNCHANGED`). An input that is unconfirmed, blocked (`ok` false), waiting (`TOO_FRESH`) or skipped creates none: its follow-ups are read, ticked or not, at the read that ingests it. There is no sweep of ingested pages (0062): a follow-up unticked after the read waits for the next read the user asks for. Marking Reviewed right after the call turns every follow-up into a Task; that is the accepted failure (0079 §4).
- **The Task.** Created with `brain sync tasks --source <the latest extract of the input>` (cli §5.14.5) and the item `{ "title": <its text>, "follow_up": "<q id>", "projects": [<the meeting's projects>] }`: the title is the follow-up's text as read (`quick` `text`); the projects are the meeting note's `projects` after this ingest; **no due date**, even when the text names one; no owner, no Scope, no page body and no marker that it came from a follow-up; the status, area and backlink of the meeting's other Tasks (the `--source` rules of cli §5.14.5).
- **Recorded, never twice.** The skill records the Task with `brain sync record` (cli §5.14.6): on the extract source `{ "tasks": [<page id>], "task_items": { "<q id>": "<page id>" } }`, and on the meeting `{ "tasks": [<page id>] }`. The `q` id is the **only** identity of a follow-up Task: a `q` id that is a key of `task_items` on the extract or on any source along its `replaces` chain never gets a second Task, whatever its text now says (`extract-plan` gives that follow-up `task: false` and its `recorded` page id; `sync tasks` refuses it), and a Task is never matched by its title. `brain source extract` carries the key forward like an item's (cli §5.23).
- **Nothing in Git but the id.** A follow-up has no quote, so its text never enters Git: not in the extract, a note, the meeting, the log or a report. Its only trace is the `q` key and the page id in `task_items`, and the page id in `tasks`. The catch-up report counts the follow-ups that became Tasks (a number, not their text).
- **The checkbox is the user's.** The brain never ticks, edits or annotates it (0007). To keep a follow-up from becoming a Task the user ticks or deletes it before marking Reviewed; there is no token for it.
- **Selection and cleanup don't reach it.** A follow-up has no subject and no passage: no `Meeting only` holds it back, `legacy_tasks` (cli §5.22) doesn't hold it back, and the exclusion cleanup (§5.2) never lists its Task (a `task_items` entry keyed by a `q` id is always mapped: never "unknown item" or "item no longer selected").
- **Older formats.** In the inline-quote and legacy shapes (§4.1, "Shapes": minutes from the earlier prompts, whose quick follow-ups carry no `q` id) 0067's rule holds: no Task from a follow-up, at a first read or a re-read. A page regenerated in the lean shape and set back to Reviewed is read in the lean shape, so its unticked follow-ups then become Tasks.
- **A regenerated summary (stated limit).** `q` ids are written once by the generator, like item ids (§4.1). When Notion AI regenerates the summary of a meeting already ingested, its follow-ups may be numbered again: a follow-up whose new `q` id already has a Task gets none, and one that got a Task under another id may get a second.
- **Held back, never silently.** The ingest report names, under Check (attended and unattended alike, since none of them blocks the input), each unticked follow-up that creates no Task: one whose `q` id already has a Task (`recorded`), one whose `q` id is on two to-dos (`DUPLICATE_FOLLOW_UP`, both named, so the user can renumber one and set the meeting back to Reviewed), and one with empty text. A to-do with no `q` id in a lean Quick follow-ups group is named there too (it stays in Notion). The catch-up report keeps these lines under its Check.
- **Module off.** With the Tasks module off, or no Tasks database, follow-ups stay in Notion as before and nothing is said about them; a later read with the module on creates them by the rules above.
- **Attended and unattended.** An attended run names them in the §4.4 preview ("<n> quick follow-ups become Tasks", with their text) and creates them with the ingest's yes; a user who wants one kept out ticks or deletes it on the page, and the skill reads the page again before writing (the page as read is what counts, §4.4). An unattended run creates them the same way, with no question (cli §6.1).
- **A run that stops** between creating a Task and recording it can create it again on a retry: the limit of cli §5.14.5, as for items.

## 7. Review: readable content with independent decisions

**7.1 One page per source; conflicts stay separate.** One Review row per source, items independently actionable; conflicts keep their own rows and the Answer workflow (0041). The Proposed property no longer carries detail: since 0.14.0 (decision 0088) `render` leaves **About, Now, Proposed and Why empty** on a row with item sections, and Notion hides each one while it is empty, because the page holds what they would repeat. Properties serve the queue: **Status** first (a Notion formula, never written by the brain: Done, Closed, Submitted: waiting for the brain, Needs you · decide in the page, Needs you · set Your call; docs/notion-space-design.md §3.10), then Name, Type, Area, About Page, Decided, Decided at, Accept all. Kind and State are the brain's and hidden. Your call and What to fix stay in the row's property group for the row-level shortcut (§7.9) and for the rows that have no sections (Conflict, Answer, Suggestion, and rows from before migration 0013).

**7.2 Item sections (page body, written by `render`, CC-79; format 1, the page of a row rendered before 0.15.0: format 2 is §7.12).**
- Heading: **`[a · it-9f2c1e44] Creates: <title>`** (a new draft note already written; a decision, question, concept or Document has no Notion page until it is accepted, 0071, so the heading links the source only) or **`[a · it-9f2c1e44] Changes: <target title>`**, with links to the target's Notion page and to the source evidence. The visible `it-…` id is the key; letters are display only, so a re-render after a defer cannot shift a decision. `item_id` is **immutable**: assigned when the proposal is created (`it-` + 8 characters from the id alphabet, unique in the proposal and generated like `proposal new` ids), stored in the proposal file, and never recomputed, so a deferral, a regeneration or a re-render cannot move a decision onto another item.
- *Current* (a quote of the existing content, absent for a creation).
- A toggle titled exactly **"Proposed final wording"** whose children are the exact proposed final wording, editable, and **may contain any blocks, headings included** (a toggle, not a heading, so its end is unambiguous). The CLI reads the children with cli §5.14.7's block-to-Markdown rules; a block it cannot convert makes the item `UNREADABLE` (it stays Pending and is shown, not applied). A toggle "Previous proposal" is never read. **Escaping:** free text that starts a line like the page's own structure is escaped by one backslash (cli §5.14.4) and the parser removes it before it hashes or applies the text; the item is `UNREADABLE` if the toggle holds anything it cannot convert.
- *Why it matters*, one line. *What Accept does* ("Accept makes this draft Reviewed" / "Accept replaces the text in <target>").
- `Decision: Pending`, and for a revision `Revision request: …`.
The skill writes this body once, at create, with the markdown page write (M9, §9). A short first-use explanation sits at the top. Tooltips (if Notion has them, §9) may add detail, never hide consequences.

**7.3 Decision tokens, Submit decisions, and when they bind.** The user types `Decision:` as `Accept`, `Reject`, `Defer` or `Request revision` (exact; M1) and edits *Proposed*. A typo makes that item `UNREADABLE`/Pending with the line shown, never a row-wide blocker. The row has a **Submit decisions** button (Edit property on This page: **Decided** → checked, **Decided at** → Now). **Nothing is read until Decided is ticked.** A second button **Submit and accept all** also ticks **Accept all**: every item whose token is `Pending` and that is eligible (not `revision_requested`, `base_changed`, unreadable or in conflict) is then treated as `Accept`; explicit tokens win. Rules by analogy with cli §5.14.7: the row is bound by `Decided at` and the page's `page_edited_at` (an edit in a **later minute** than Decided at invalidates the row's *unapplied* decisions; the user submits again; the click-minute limit of decision 0058 applies); the skill **re-reads the page just before applying** and each item's *Proposed* hash and token must equal what was planned (else that item is dropped as `CHANGED_SINCE_PLAN`); an attended run shows each item's action, target and exact final text as the record of the user's decision, not as a question (below); an **unattended** run applies only items whose decision is explicit, exact, current, deterministic **and whose Decided at is at least 2 minutes old** (§8).

**An attended run applies a submitted acceptance without asking again (0055).** An item the user accepted on the page and submitted is decided: the wording they accepted is the decision, and there is no second approval of the user's own wording (0055). When the user asks to apply their reviews or to catch up, the attended run shows each item it will apply (its action, its target and the exact final text, with a correction named as the user's, §7.7) as a statement of what the user decided, then re-reads the page and plans again just before applying (above), and applies the items that are unchanged and eligible without waiting for a yes. *Submit and accept all* is such a submission for every item it accepts. The user's request sets the scope ("apply my reviews" covers every submitted row; "apply the launch review" covers that row), and the run never widens or narrows a submission by guessing. A **fresh acceptance**, a new Submit on the page, is needed, and nothing is applied for the item until it comes, when:
- its wording or its page changed after the submission was read (`EDITED_AFTER_DECIDED`, `CHANGED_SINCE_PLAN`): the user submits again;
- its base changed (`BASE_CHANGED`, §7.6): *Current* is re-rendered and the token is back to `Pending`;
- it is a drafted revision: a revision request is not acceptance of the draft it produces (§7.8); the draft applies only after the user accepts it, exactly, in a later submission, never in the run that drafted it;
- it is held for any other reason (unreadable, a missing section, a conflict, excluded evidence): it is shown with what to do, never applied by interpretation.

When the user's words leave the scope ambiguous (two rows or items match), the run asks which before applying anything of them. Rows of the old layout keep §7.9; a revision is drafted by §7.8. This changes what the run asks, not what it checks: the re-read, the hashes, the base check, the exclusion check (eligibility.md §9.2) and the attribution of corrections (§7.7) all hold. **Stated limit (the click-minute limit of 0058, as unattended):** an attended run may apply a submission whose Decided at is less than 2 minutes old, so an edit made in the minute of the Submit click and before the first read is read as part of the submission; the shown text is how the user sees what was taken. A Document's or report's accepted wording is not a Review item and keeps 0058's attended yes (cli §5.14.7).

**Precedence (normative; format-1 rows: a format-2 row is decided by Your call, §7.12.7).** For an item: an explicit item token (read after Submit) > a row-level Your call Approve/Reject on a new-layout row (read without Submit, applying each item's stored proposal text) > the legacy What to fix (old-layout rows only). A row-level call never overrides an item with an explicit token. If any item's *Proposed* was edited, a row-level Approve/Reject is refused for the row (`EDITED_PROPOSED_NEEDS_SUBMIT`). An edited pending section is never discarded by any of them.

**7.4 Consuming a submission, and our own writes (guarded).** The brain **never rewrites a whole Review body after a submission.** Three hashes per item, none of them confused: `rendered_hash` (the section as the brain last rendered it, used only to detect edits **before** a submission), `submitted_hash` (the section exactly as read at the Submit that the run is acting on, stored in `item_decisions` as `snapshot_hash`), and the item's canonical state in the proposal file. The user is **expected** to differ from `rendered_hash` (they type `Decision: Accept`, they edit *Proposed*); that is not a conflict. After applying, the brain writes in this order. (a) **The top summary block and the properties** (State and a decided/applied count): a brain-owned block with a stored block id, rebuilt entirely from the proposal file, marked do-not-edit. It keeps the counts ("3 of 5 decided: 1 applied, 1 closed, 1 deferred, 2 waiting for you") and then names **each item's outcome** on its own line, by its letter and the title its section heading uses ("c · Budget on Acme website — Deferred to …"), so the user never works out from counts which items still need them (CC-214). The outcome comes from the item's canonical state, found by its `item_id`, never by its letter: applied (with the user's own wording when they edited it), rejected, closed without being applied (it rests on text the user excluded, or its target changed first; never called a rejection), deferred, a revision requested, a revised wording waiting for a decision, held, or waiting for a decision. A deferred item names the Review row it now waits in, following later deferrals to the last one, and links that row's page only once it is published; until then the line says it awaits publication. The summary reports decisions, never makes them, and shows no wording or value: a title is the one the section heading shows, so a restricted one stays withheld (cli §5.14.4 has the exact lines); because it is brain-owned and derived, it is simply rewritten each run and a failed write is retried at the next run from the proposal file (idempotent), with no guard needed beyond the block id. (b) **Only the item sections that need something the user must see in them**: a revision the user requested, a changed base (*Current* updated) or a new draft. **An applied or closed status is never written into an item section.** Each such section is written one at a time, and only if it still equals `submitted_hash`, i.e. nothing changed **after** the submission was read. If it differs, the user edited after submitting: the skill does **not** overwrite; the proposal file keeps the item's canonical state **unchanged** (an item already `applied` stays applied and is never reset to Pending or applied again, §7.11); the page shows beside the section a toggle "Brain update" with what the brain would have written, and for an applied item the summary block (a) carries the line "b: applied; you edited its section after submitting, your edit is kept: submit again to change it". After each own write the skill records the new section hash and advances the expected page fingerprint and `page_edited_at`, so a multi-item submission is not blocked by the brain's first write. A newer submission (a later **Decided at**) always wins and is read next run. Only after the summary and any section writes does the skill clear **Decided, Decided at and Accept all**, under the same guard (the page still shows that Decided at and the same decision-lines fingerprint). Invalidation is row-level for unapplied items.

**Stated limit, accepted by the user (2026-11-01, option C).** Between the re-read and the write, and inside one minute of timestamp resolution, an edit to a section can still be overwritten; reading the page and writing the section are two calls, so this is a guard that narrows the window, not an atomic compare-and-swap, and the Notion API cannot close it. **Mitigation chosen: write less into sections the user can edit.** Applied and closed status goes in a **brain-owned summary block at the top of the page** ("3 of 5 decided: a applied, b closed, c waiting for you") and in properties (State, a count), not into each item section; the brain rewrites an item section **only when it has something the user needs in it**: a revision the user requested, a changed base (*Current* updated), or a new draft. In those cases the user is usually waiting for the result. The residual window is documented in the guide, and Notion's page history recovers an overwritten sentence; nothing canonical is lost, because decisions and data live in the proposal file.

**7.5 What each kind's *Proposed* is, and what Accept does.**

| Kind | *Proposed* holds | Editable | Accept |
|---|---|---|---|
| Creation (`Creates`, a draft note) | the note's body text | yes: the edit is written into the draft's body | note becomes `reviewed` |
| `update_fact` | the new value | yes (validated as an `edit`, `INVALID_RESULT` if not) | value applied; `before` is the base |
| `update_body` | the new body | yes | body replaced; `before_hash` is the base |
| `add_to_note` | the Markdown appended | yes | appended after the note, with `Source:` |
| `replace_line` (0.15.0) | the new line | yes: one line (`INVALID_RESULT` if not) | that one line replaced; `before_hash` is the base |
| `add_link` | the values added to the list field | yes (values) | links added |
| `supersede`, `merge`, `contradiction`, `answer` | a description of the effect | no: Accept, Reject, Defer or Request revision only | the §11.2 effect (there is no editable text; an `answer` keeps its Answer-row workflow, 0041) |

**Base per kind.** Creation: the draft note's body hash at render (an edit of *Proposed* is checked against it). `update_fact`: `before`. `update_body` and `replace_line`: `before_hash`. `add_to_note`: `before_hash` of the target body at render (a changed body makes the item `base_changed`, so an appendix is re-shown against the new text). `add_link`: the list field's current values at render (a changed list makes it `base_changed`). A missing target makes either `base_changed`. Conflict rows and Answer rows keep their own pages and workflow (0041) and are never items of this page.

**7.6 Per-item outcomes and the row's state.**

| Token | Creates | Changes | Item state |
|---|---|---|---|
| Accept | note `reviewed` | for an editable kind the *Proposed* text applied exactly, for the others the §11.2 effect | `applied` |
| Reject | the draft is archived by the existing reject rule (§11.2) | nothing changes | `closed` |
| Defer | stays draft; item moves to a **new pending proposal** (the deferral rule of §11.3) | unchanged; item moves | `deferred` |
| Request revision | stays draft; `revision_requested` | unchanged | `pending` |
| Pending / **missing section** | unchanged | unchanged | `pending`: a missing section is never an implicit decision (the next render restores it from the proposal file) |

**State machine (amends §11.1).** The proposal's `status` stays `pending` while any item is `pending`; `item_decisions` (`{item_id, decision, decided_at, decided_by, proposed_hash, base_hash}`) records decided items, applied atomically **per item** at each catch-up; the proposal becomes `applied` when no item is `pending` (all `closed` is `closed`). **Terminal states:** a deferred item is terminal in this proposal (it lives on in its new one); `revision_requested` is `pending` until a new draft is decided; when no item is `pending`, the proposal is `applied` if at least one item was applied, else `closed`. A base change (`before`/`before_hash` no longer match) makes the item `base_changed`: not applied, re-rendered with the new *Current*, token reset to `Pending`, no silent merge. **Row-level Your call** (old Approve/Reject) is a shortcut: Approve = Accept all, Reject = Reject all, for items with no explicit token; an item with an explicit token keeps it.

**7.7 Corrections are authoritative and attributed.** If the user edits *Proposed* from "March 15" (what the source said) to "March 18" and accepts: the fact's current `facts.<field>` is March 18; its timeline keeps the source's entry (March 15, `source` = the extract, never rewritten and never attributed to the user; it is marked `superseded` because the user's value replaces it) **and** a new entry (value March 18, `source` = `user-correction:<proposal id>`, `assessment: accepted`, `learned` = the decision date). The brain never claims the source said March 18.

**7.8 Request revision.** The user writes the instruction on the line `Revision request:` under the item, or, on a format-2 row, sets Your call to Request revision with What to fix, which an attended run maps to the items it names (§7.12.7). The next draft replaces *Proposed*, keeps the user's previous edited text in a toggle "Previous proposal", and returns `Decision: Pending`. The brain never accepts a draft for the user. Unattended runs **never read** revision text (0051). Editing or deleting *Proposed* changes the proposal only; it never deletes the target note.

**7.9 Legacy rows keep their semantics (CC-79 `sync plan`, deterministic).** A Review row rendered **before** migration 0013 has the old layout (the Proposed property) and keeps the 0045 behavior until it is terminal: Approve, Reject and Fix with What to fix are read exactly as today (`NOTE_TO_READ`, `FIX_TO_READ`, `FIX_WITHOUT_TEXT`; a Fix means "apply it, corrected as written", not a new draft), with no Submit step and no conversion. Migration 0013 **adds** the Your call option **Request revision** and **does not rename Fix**. On a row of the **new layout**: a row-level Approve or Reject is read as it is today without a Submit (`decided_at` = `last_edited`) and applies each item's stored proposal text, but is **refused for the row with `EDITED_PROPOSED_NEEDS_SUBMIT`** when any item's *Proposed* was edited (the user submits instead); a row-level **Fix** or **Request revision** on a new-layout row is the conflict `ROW_REVISION_NOT_SUPPORTED` (use Request revision on an item). Nothing pending is lost, nothing is converted, and unattended runs treat all of it as today (0051). On a format-2 row (§7.12) Your call decides the page instead, and `EDITED_PROPOSED_NEEDS_SUBMIT` and `ROW_REVISION_NOT_SUPPORTED` don't apply (0090 §5).

**7.10 Publishing preserves pending edits.** `render` never rewrites a Review row's body while any item has an edited *Proposed*, a non-`Pending` token or `revision_requested` (`REVIEW_PENDING`, as `WORDING_PENDING` in cli §5.14.7), except the re-render of §7.4 after a consumed submission.

**7.11 Partial apply, recovery and missing text.** *Operation and recovery (CC-78, CC-79).* Every multi-file write of this contract (a new extract version with its suppression record and views; an item's target note plus its proposal file) follows one protocol. (1) Before writing, the command writes `_journal/<op-id>.json` with the paths it will touch and, for each, the hash of its new content (a path that does not exist yet is listed as new); (2) it writes the files; (3) it commits (every operation already ends in a git commit); (4) it deletes the journal. At the start of **every command, reading or writing** (`query`, `index`, `views`, `lint`, `status`, `reflect`, `sync plan`/`render`/`apply`, and the skills' read-only passes), if a journal exists the command **refuses with `RECOVERY_NEEDED`** until recovery has run; only `brain recover` (CC-78 adds it) and the write commands may run it. Recovery: if the commit carrying the trailer `Op: <op-id>` exists, delete the journal; otherwise restore each listed path to the last commit (`git checkout -- <path>`) and remove each listed new path, then delete the journal and report `RECOVERED <op-id>`. Every step is idempotent, so an interrupted recovery is simply run again; the journal is deleted **last**. If recovery fails (a path cannot be restored, git is unavailable) the journal is kept and every command keeps refusing: the brain fails closed and never proceeds on a partly rolled-back tree. The operation's commit carries `Op: <op-id>` so the journal and the commit identify each other durably. A working tree that is dirty without a journal is refused (`DIRTY_TREE`), not recovered. So a crash between writes leaves either the old state or a journal that the next run undoes: no half-restricted brain and no half-applied item. *Idempotence.* `item_decisions` records an item `applied` in the same commit as its write set, so the commit is the journal of record: after recovery an item already `applied` is never applied again (by `item_id`), a pending one is re-planned. A Notion write that fails after some sections changed is completed idempotently from the proposal file on the next run. An item whose *Proposed* text is **empty, missing, or unreadable** (a block that cannot be converted) is `UNREADABLE`: it stays Pending, is shown, and is never applied or treated as a deletion. Two decisions for the same item (a re-submission before the first was applied) resolve to the later **Decided at**.

**Product decisions (user, 2026-11-01).** (1) Granularity: **paragraph**, fail closed (§4.2); collisions measured in U-23; sentence-level or an explicit per-case override are follow-ups if they are frequent. (2) Read-to-write window: **accepted with mitigation C** (§7.4: status in a top summary block and properties; item sections rewritten only for a requested revision, a changed base or a new draft). CC-78 and CC-79 are unblocked.

**7.12 The Review page, format 2 (0.15.0; decisions [0088](../decisions/0088-a-review-row-says-it-needs-you-and-a-review-page-reads-plainly.md) §2, [0090](../decisions/0090-review-by-grill-notion-ai-reviews-with-you-and-your-call-decides.md); CC-240).** From 0.15.0 a Review page with item sections reads plainly, can be reviewed with Brain Assistant, and is decided with Your call. §7.2 to §7.11 hold for it except where this section says otherwise; a page rendered before keeps §7.2 to §7.11 exactly (format 1).

*7.12.1 Which rows, and the one rebuild.*
- **The format is recorded.** The render that writes a format-2 body records `published["@review"].format = 2`. A `@review` without `format` is format 1. The parser and the rules of a row follow its recorded format, never a guess from the page.
- **New rows are format 2** whenever item sections are on (`notion.review_sections`, §10), unless `brain.json` `notion.review_format` is `1` (schema §12), which keeps new pages in format 1 and rebuilds nothing.
- **Untouched rows are rebuilt once (0088 Q8).** A published pending `review_notes` row of format 1 is rebuilt as a new format-2 page at the first publish that knows it is untouched: the plan read its page (`review` in the snapshot), every section is there once with `Decision: Pending`, no Proposed was edited, no `Revision request:` line has text, Decided is unticked, Your call is empty, and the proposal has no `item_decisions` and no `revisions`. `sync plan` lists such rows in `review_untouched`; `sync render --plan` rebuilds them (cli §5.14.4). The skill creates the new page, writes its body, records it, then moves the old page to Notion's trash; the report says how many rows were rebuilt. A row the plan did not read, or that anyone touched, keeps format 1 and its rules until it is done. A rebuilt row keeps its proposal, its items and their ids; only the page is new.

*7.12.2 The page, top to bottom.* In this order:
1. **The top**, written once (it says what the source brought, which does not change):
   - `**From <source title>:** <counts>.` with the title rule's counts (cli §5.6: changes, new notes, links, a link counting each value), then one sentence on the marks: `⚠ marks a change to something you already know and ⚑ something the brain is unsure about: Approve leaves both until their line says Decision: Accept.` The sentence names only the marks the page has, and never suggests accepting.
   - `**What to do:** 1. Read the sections below, or click **Review with me** to go through them with Brain Assistant. 2. Correct a wording where it stands, or type Accept, Reject, Defer or Request revision on an item's Decision line. 3. Set **Your call**: Approve, Request revision (say what in What to fix) or Reject.`
   - `Source: [<source title>](<url>)`, the only link to the source on the page (omitted while the source has no page).
2. **`## Review summary`**, brain-owned and rebuilt by every render that sends the row (§7.4 a): its first line is the status. While no item is decided it counts what waits by group: `**Status:** waiting for you: 2 changes, 3 new notes and 3 links.` (only the groups that have items; links count values). Once an item is decided, or a plan holds one, it is `**Status:** ` followed by today's count line, then one outcome line per item (cli §5.14.4), each item named by its heading; an item the plan held shows `Held: <the reason in words>` instead of waiting.
3. **`## What this meeting was about`** (`What this document was about` for any other source), only when the proposal lists the source's own summary note: the `meeting` note whose id is the proposal's `source`. Its one item section comes first (0088 Q10). It is still an item: Accept makes it Reviewed.
4. **`## Changes to what you know`**: the `changes` items, in stored order.
5. **`## New notes`**: the other note items, in stored order.
6. **`## Links`**: the link items, in stored order.
6a. **`## Needs clarification`** (0.15.0), on a correction group with `needs_clarification` only (weekly-review.md §8.4): one line per match, `- <note title>: <line>` (`- <note title>: its <field> fact` for a fact), never an item and never read. On a correction group the top's first line is `**Correction:** <counts>.` instead of `**From <source title>:** <counts>.`
7. **`## For Brain Assistant (brain context)`**, a toggle heading at the end (§7.12.5).

A group with no items has no heading. Group headings and the top are never read.

*7.12.3 An item section.* Each item is one `###` heading and the lines under it, up to the next heading:
- **The heading** says what Accept does, with the note type, and is derived from the item's state at each render (0090 §4: never read):
  - the summary note: its title;
  - `update_fact` with a current value: `⚠ <Field> on <target>: <before> → <after>`; without one: `<Field> on <target>: <after> (new)`;
  - `update_body`: `New text for <target>`; `add_to_note`: `Adds to <target>`; `replace_line`: `⚠ Line in <target>` (0.15.0);
  - a new note: `New <type>: <title>` (`New person: Ana Ortiz`, `New decision: Use Supabase for auth`, `New Document: …`); the type is the note type's plain name;
  - a link item: `<Field> on <target>` (`People on Website refresh`); an `aliases` item: `New alias for <target>`;
  - a held item: `Held: <title>` (§7.2's stub rules; nothing else in the section but the `ref` and `Decision:` lines);
  - `⚑ ` before the heading when the item has an unsure flag (§7.12.8).
- ***Now*** for a fact or body change only: `> Now: <value>` for `update_fact`, and `> Now:` followed by the current body as a quote for `update_body`, and `> Now: <line_before>` for `replace_line`. An `add_to_note` shows no Now and no "end of the note" quote: the heading says it adds.
- **The wording**, visible (0088 Q6) for a change and a link item: the proposed text as lines of the section. A fact's wording is its value followed by its markers (`2027-03 [¶4]`). A link item's wording is one line per value, `+ <name>` (`+ Ana Ortiz`, sent as `\+ Ana Ortiz` so Notion keeps it a line, not a list), a note named by its title. A new note's wording is the note's body inside a toggle **Read or edit the note**, since a body can run to dozens of lines.
- **Why**, only when it says something specific: `*Why: <text>*` when the change's own `why` exists and differs from the proposal's `why`. A note or link item has none.
- `<span color="gray">ref it-9f2c1e44</span>`: the item id, gray, on its own line, out of the heading.
- `Decision: Pending`, and `Revision request: …` for a revision, as §7.3 and §7.8.
- A toggle **Previous proposal** after a drafted revision, never read (§7.8).

No title line under the heading, no source link per item, no per-item "What Accept does": the heading's verb says it and the top explains it once. A section a render rewrites (§7.4 b) is rebuilt by the same rules.

*7.12.4 Markers and escaping.*
- **Short markers (0088 Q7).** A passage reference `^[src-…#¶72:55476822]` in wording is shown as `[¶72]`. A fact or link item cites its item's passages that are passage references, as labels after the value (`2027-03 [¶4]`; a link item shows none). A label is unique on the page: when two passages of the page share a paragraph number, each shows as `[¶72 src-xxxxxxxx]`. Markers are never hidden, because an edit would drop them.
- **Expanded on read.** The parser turns each label back into its full reference from the page's passage list: the passages of every item on the page, which are what the brain-context toggle lists (§7.12.5). A label the list doesn't hold makes the item unreadable (`UNKNOWN_MARKER`): it stays Pending, is shown, and is never applied. A label of a passage the page lists but the item doesn't is accepted only when the wording changed (0090 §4: the marker may move to another listed passage); the 0077 check then runs on the item's passages and the passages its wording cites, together.
- **Escaping.** Wording that would read as page structure is escaped by one leading backslash, as §7.2: a line that starts (after blanks and backslashes) with `#`, `>`, `*Why:`, `ref `, `<span`, `<details`, `</details>`, `<summary`, `Decision:`, `Revision request:` or `Agreed in review:`, and a `[¶n]` written in the source's own text (the label form is the brain's). The parser removes one backslash before it hashes or applies.

*7.12.5 The brain-context toggle (0090 §2).* The toggle heading `## For Brain Assistant (brain context)` closes the page. Its children are rebuilt by every render that sends the row (a section, like the summary), and are **never read** as wording: the parser stops at that heading. They hold, in this order, each under a bold label:
- **Source passages:** each passage the page cites, `[¶n] <its text>`, from the source's extract;
- **What each item changes:** per item, `<heading> (ref it-…)`: its target, its current value or the end of its body, and what Accept does (the words of §7.5);
- **Where the brain is unsure:** each flag of §7.12.8 with its item's heading, or `Nothing flagged.`;
- **Repeats:** each group of items that record the same thing, `<headings> record: <what>`, or `None marked.`;
- **Related pages:** the source, the project or area and the meeting, as page links (the row's relations stay as they are);
- **Rules for writing into this page:** the rules of 0090 §4 in plain words (only item sections; the wording, the Decision line, the Revision request line, a marker moved only to a passage listed above when the wording changed, one `Agreed in review:` line under a section it changed; never a heading, a `ref` line, a toggle's structure, this toggle, any property or Your call).

A line of the toggle never starts like an item's structure (`ref `, `Decision:`), so a page whose toggle heading was deleted still has no item there.

*7.12.6 Reading the page back (`sync plan`, format 2).*
- **Items are found by their `ref` line (0090 §4).** The page is split at its headings outside toggles; a part with exactly one `ref it-…` line is that item's section; a part with none (the top, the summary, a group heading) is not read. Headings are never read: an edited heading changes nothing, and the next render that writes the section restores it. Two parts with the same id are `DUPLICATE_SECTION`; a part with two `ref` lines is read as neither item (`MISSING_SECTION` for both, unless their id appears alone elsewhere).
- **The wording** of a change or link item is its lines that are not structure (the heading, *Now* quotes, `*Why:` lines, the `ref` line, the `Decision:`, `Revision request:` and `Agreed in review:` lines, toggles), unescaped, labels expanded, canonical; of a note item, the children of **Read or edit the note**. A section whose toggle is missing or holds an unconvertible block is `UNREADABLE_PROPOSED`, as §7.2.
- **A fact's value** is its wording without its markers; a wording of more than one line is `INVALID_RESULT` at apply, as an edited fact today.
- **A link item's values** are its wording lines, each without a leading `+`, `-` or `*` and blanks, matched to the item's values by title, alias or id, ignoring case. A value the user deleted is not added; Accept adds the rest (0088 Q5). A line that matches none of the item's values makes the item unreadable (`LINK_VALUE_UNKNOWN`): editing never adds a person; with no line left the item is `UNREADABLE_PROPOSED`, never a deletion (Reject adds none).
- **`Agreed in review:` lines (0090 §4)** are not wording: they are left out of the hashed text and stored in the item's `item_decisions` entry as `agreed` (schema §11), so the reason for a correction stays in Git.
- **`VALUE_NOT_IN_PASSAGE` (0090 §4).** An accepted `update_fact` whose value appears in none of the passages its wording cites (its markers; with none, its item's passages) is held: it stays Pending, is never applied, and Approve leaves it. The value is matched by its type: a number as digits or as words (`9`, `nine`); a date in any form that names the same day, month and year at the value's precision (`2027-03`, `March 2027`, `Mar 2027`, `03/2027`; a day's date may leave out the year); a name as the value or an alias of the note it names; a status or other select value as the option's name; any other value as its text, ignoring case and surrounding punctuation. When another passage the page lists holds the value, the hold names it (`¶4 says 9`). Only passage references are checked: a fact citing whole inputs only is not (a stated limit).
- **Anything else outside the rules** (a missing `ref` line, a broken `Decision:` line, an unknown marker) keeps §7.3's outcome: the item is unreadable, stays Pending, and is shown, never applied by interpretation.

*7.12.7 Your call decides a page (0090 §5; amends §7.3's Precedence and §7.9 for format-2 rows).* No Submit is needed: the row's **Your call** is the submission, its time the row's `last_edited` (with 0058's click-minute limit, as for a row-level call today), and the plan reads the page with it.
- **Approve** submits the page as it reads now. Each item's `Decision:` line is its decision; an item still on Pending is read as Accept, **except** a ⚠ fact change (an `update_fact` with a current value) or an item with an unsure flag: those are accepted only by an explicit `Decision: Accept`, so Approve leaves them Pending (`NEEDS_EXPLICIT_ACCEPT`) and the row needs the user again. Items not eligible (a requested revision, a changed base, held, unreadable) are not applied either. Edited wording no longer blocks Approve: the edited wording is what is applied.
- **Request revision** (or **Fix**, the option's name on a space that still has it) with What to fix asks for redrafts. `sync plan` lists the row in `review_row_revisions` with the text; nothing else on the page is read. The next **attended** run maps the text to items and records one revision per item (§7.8), drafts them, writes them into their sections, and clears Your call and What to fix, so the row needs the user again. An unattended run never reads the text, records nothing and leaves the row as it is (0051). Request revision without What to fix is the conflict `REVISION_WITHOUT_TEXT`.
- **Reject** rejects every item still on Pending; an item with an explicit `Decision:` keeps it. Rejecting changes nothing in the brain: a rejected fact change leaves the field as it is now (an empty field stays empty), a rejected addition or link is not made, and a rejected new note is archived (0041).
- **Clearing.** Once a run has consumed the call (applied what it could, or recorded the revisions), `sync apply` names the row in `review_clear` and the skill empties Your call and What to fix, under §7.4's guard (the page still shows what was read). An item Approve left stays Pending on the page, and the summary says why.
- **What the guide and the grill's preview say:** "Reject leaves the note as it is now. Approve accepts what's still Pending, except ⚠ changes and flagged items, which need Accept on their line. A redraft you ask for comes back on this page after your next catch-up, and the row needs you again."
- **Decided, Decided at and Accept all** are not read on a format-2 row: the Submit buttons leave the Review layout (migration 0025, CC-241): they stay reachable under the row's *Show all properties*, so a format-1 row the user already touched can still be submitted. `EDITED_PROPOSED_NEEDS_SUBMIT` and `ROW_REVISION_NOT_SUPPORTED` don't apply to it. Format-1 rows keep §7.3 and §7.9 until they are done. A cleanup row (cli §5.6 `cleanup`) is always format 1: it is never rendered in format 2 and never rebuilt.

*7.12.8 Unsure flags and repeats (0090 §6).* An item carries `unsure` (a list of one-line flags) and `repeat` (a short key shared by the items that record the same thing), both stored in its `items` entry (schema §11):
- **Judged by the ingest** (CC-241's skill): two passages of the source giving different values, a value chosen between readings, a person or project matched by name only. Each flag names both passages and the reading chosen, and says the ingest judged it.
- **Found by the CLI**, at render and plan, never stored: two `update_fact` changes of one proposal on the same target and field with different values flag both items (`Two values for <Field> on <target>: <a> and <b>.`).

A flagged item gets `⚑` in its heading and Approve leaves it (§7.12.7). Repeats are listed in the brain-context toggle; they change no decision.

*7.12.9 Hashes.* `proposed_hash` is over the canonical wording with labels expanded, `Agreed in review:` lines left out and blank lines dropped (they are layout: Notion may add or remove them), which is exactly what is applied (for a link item, its value lines); `rendered_hash`, `base_hash`, `snapshot_hash` and the re-read before apply are §7.4's. An accepted item is bound to the wording the page showed when it was read: the skill re-reads the page before applying, and a section changed since the plan is `CHANGED_SINCE_PLAN`.

*7.12.10 Review with me and the Grill review skill (0090 §1, §3, §4; CC-241).* The row's button **Review with me** (property `Grill`, migration 0025) sends Brain Assistant a message that names the skill and the page (0054's button pattern, docs/notion-space-design.md §3.16). Unlike the other Brain Assistant buttons, the message carries no confirmation to write: the skill asks for a yes to its preview. The skill's text is in notion/brain-assistant.md; what the brain reads back is §7.12.6, whatever the skill writes. The skill:
- **Works only on a format-2 page** of a pending row: one with `ref it-…` lines and the brain-context toggle. A format-1 page (headings `## [a · it-…]`) gets a one-line pointer to the hand path, and a row with Your call already set is left alone.
- **Grills in rounds** of three to five questions, most important first, in 0090 §3's order, each question with lettered options as a list, the recommended one marked with one line on why. One blank line separates two questions and two options (the round trip found them cramped).
- **Shows a preview and waits for a yes** before it writes anything: per section, its heading, the new wording exactly, each moved marker, each `Decision:` line and each `Agreed in review:` line it will write; then §7.12.7's sentence.
- **Writes a `Decision:` line only as the user chose it** (settles the round trip's first deviation). Accept, Reject or Defer is written on an item only when an answer chose it for that item; agreeing on a wording is not an Accept. A ⚠ or ⚑ item needs that explicit Accept, or Approve leaves it (§7.12.7), so the last round asks, for each one still on Pending, whether to accept it, and the preview says which Accept lines are the ones Approve needs. The skill never writes Request revision on a `Decision:` line: a redraft is asked for on the `Revision request:` line or with Your call.
- **Writes `Agreed in review:` only under a section whose wording it changed** (settles the second deviation): one line, what the user decided and why, in a few words. A section where only the `Decision:` line changed gets none. The parser stores any such line it finds (§7.12.6), so a stray one is harmless, but the skill doesn't write it.
- **Never** writes a heading, a `ref` line, a toggle's structure, the brain-context toggle, a property or Your call, and never recommends Approve or Reject for the row. Something found only in Notion is said to come from Notion, and enters the wording only with the user's yes, with the `Agreed in review:` line saying so.

The cost of a run in Notion AI credits is not measured yet (§9.6).
